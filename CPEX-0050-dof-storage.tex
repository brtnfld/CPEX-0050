\section{Abstract}
%% ═════════════════════════════════════════════════════════════════════════

This CPEX introduces a \texttt{DofStorage\_t} enumeration and corresponding
SIDS node to the CGNS standard, enabling CGNS files to explicitly record how degrees of
freedom (DOFs) are stored relative to shared mesh entities.  The two values---\texttt{DofStorageShared}
and \texttt{DofStorageIndependent}---answer a single question: for DOFs located at a geometric entity
(vertex, edge, or face) that is shared between adjacent elements, does each adjacent element
index the \emph{same} buffer slot (shared storage), or does each element own its
\emph{own} independent slot (independent storage)?  The question is always posed relative to
a stated reference entity set---for a block indexed over volume elements those are the volume
elements; for an interface block they are the volume elements adjacent to each listed face or
edge (Section~\ref{sec:dofstorage-interp}).  This is a statement about data layout
only; it makes no claim about the mathematical smoothness of the resulting field.

The gap being closed is specific.  For every encoding legal today, the DOF layout is already
fixed by \texttt{GridLocation\_t} together with the SIDS \texttt{DataSize} rules, so this
proposal is not a remedy for ambiguity.  What cannot presently be expressed at all is an
element-local layout at a shared-entity grid location: a solver storing per-element solution
values at positions that coincide with shared mesh vertices has no conforming encoding, and
the workaround observed in practice is to duplicate the grid coordinates, destroying the
shared-vertex connectivity that mesh walking depends on (Section~\ref{sec:field-evidence}).
Accordingly \texttt{DofStorageIndependent} at \texttt{GridLocation\_t = Vertex}, together with the
\texttt{PointList} ordering rule of Section~\ref{sec:shared-vertex-layout}, is the
load-bearing content of this proposal; \texttt{DofStorageShared} is retained for explicit
self-description of the layout that the connectivity already implies.  The node is defined
for any polynomial order and any discretization family, and complements---without
duplicating---the higher-order solution infrastructure of CPEX~0045~\cite{cpex0045} and the
integration-point infrastructure of CPEX~0047~\cite{cpex0047}, both of which are
element-local by construction and require no such designator.

A second, independent attribute, \texttt{InterfaceContinuity\_t}, records something the
storage layout cannot: where DOFs are duplicated at element interfaces, whether the copies
agree by construction.  A continuous spectral-element field stored per element and a
discontinuous Galerkin field stored per element are indistinguishable in CGNS today---same
grid location, same sizing, same basis---yet only the former may be safely welded into a
continuous reconstruction.  This attribute is optional, is not verified by the library, and
is orthogonal to \texttt{DofStorage\_t}; it is the one item here that no other CGNS metadata
supplies.

\section{Motivation and Rationale}
%% ═════════════════════════════════════════════════════════════════════════

\subsection{Problem Statement}

Modern CFD and computational mechanics codes increasingly use
discretization methods whose solution data cannot be fully described
by the existing CGNS metadata~\cite{cgns-sids}.  The core issue is the
treatment of degrees of freedom (DOFs) at shared geometric entities
(vertices, edges, faces):

\begin{itemize}[leftmargin=2em]
\item In a \textbf{shared} layout (e.g., Continuous
  Galerkin FEM, $C^0$ spectral element methods), DOFs at shared
  interfaces are \emph{shared}: a single value exists per geometric
  node, and the global solution field is at least $C^0$-continuous
  across element boundaries.

\item In an \textbf{independent} layout (e.g., Discontinuous
  Galerkin~\cite{hesthaven2008,cockburn2000}, finite volume,
  $C^{-1}$ spectral element methods), DOFs
  are \emph{element-local}: each element owns its own values at every
  point, including at shared interfaces.  Multiple independent values
  may exist at the same geometric location.
\end{itemize}

This distinction affects:

\begin{enumerate}[leftmargin=2em]
\item \textbf{Data size and layout.}  A DG solution on a mesh with
  shared vertices stores more values than a CG solution on the same
  mesh.  Because the SIDS sizing rules for \texttt{Vertex} admit only
  the shared count, such a solution cannot be written at that grid
  location today; once a second sizing is admitted, a machine-readable
  discriminator is required so that readers can tell which of the two
  is in use.

\item \textbf{Visualization and interpolation.}  Shared-DOF fields can be
  interpolated globally using the mesh connectivity; independent-DOF fields
  require element-local interpolation and may exhibit intentional
  discontinuities at element interfaces that should not be smoothed.

\item \textbf{Restart and data exchange.}  Solvers reading restart
  files, and coupling frameworks exchanging data between codes, must
  know whether DOFs are shared or element-local to reconstruct the
  solution state and select the correct transfer operators.  Where the
  grid location already settles that question this is a matter of
  convenience rather than necessity; where it does not, it is the
  difference between a usable file and an unreadable one.

\item \textbf{Error estimation and adaptation.}  The jump in solution
  values across element interfaces in a DG solution is physically
  meaningful and is used for error estimation.  A post-processor that
  incorrectly treats DG data as shared-DOF data would average out these
  jumps.
\end{enumerate}

\subsection{Evidence from Practice: Grid Duplication as a Workaround}
\label{sec:field-evidence}

The requirement addressed here was raised by implementors of third-party
CGNS readers, whose difficulty is concrete rather than
theoretical.\footnote{Raised in correspondence with the CPEX champion,
April 2026.  Specific parties and codes are intentionally not
identified.}  The substance of their report, paraphrased:

\begin{quote}
At least one DG solver in production writes \emph{duplicate grid
coordinates} for nodes that are geometrically shared, so that the grid
and the solution have matching extents and existing readers will accept
the file.  What is needed is a designator for the case of shared nodes
in the grid but independent solution values at those nodes.  Retaining
shared grid nodes is what permits walking through the mesh---stream
tracing, for example.
\end{quote}

This is the expressiveness gap of Section~\ref{sec:prior-art} observed
in the field, and it is the primary justification for this proposal.
Because no designator exists, a solver wishing to emit element-local
solution values at vertex positions must instead \emph{explode the
mesh}: every element receives its own copy of each vertex, the
\texttt{GridCoordinates\_t} array grows by the average vertex valence,
and the shared-vertex connectivity that makes mesh walking possible is
destroyed.  The cost is borne twice---once in file size, and again by
every downstream reader that can no longer traverse the mesh.

Two points about this evidence deserve emphasis, because they determine
how narrow the proposal should be:

\begin{itemize}[leftmargin=2em]
\item The requirement is specifically for \emph{independent} DOFs at
  \texttt{GridLocation\_t = Vertex} while the grid retains shared
  vertices.  It is a request for one designator value, not for a
  general classification of DOF storage.
\item The constituency is third-party \emph{readers}, not solver
  authors.  This is what distinguishes this proposal from the
  alternative of requiring CPEX~0045's \texttt{InterpolationPoints}: a
  reader that must implement \texttt{Family\_t}-level
  \texttt{SolutionInterpolation\_t} lookup, basis evaluation, and
  control-point handling in order to interpret a first-order DG field
  bears a cost out of proportion to the data.  Where the DOF positions
  simply \emph{are} the mesh vertices, the difference is between
  reading one additional scalar node and implementing an interpolation
  framework.

  No claim of earlier availability is intended or implied.  This
  proposal and CPEX~0045 are being developed together and target the
  same release, so neither is the faster route to the capability; the
  argument for this one rests on reader-side implementation cost alone.
  Joint development is itself the reason the two can be relied upon to
  interlock: shared vocabulary, a single pass through the MLL and
  \texttt{cgnscheck}, and no possibility of the two describing the same
  data in contradictory terms.
\end{itemize}

\paragraph{A second, independent instance of the same workaround.}
The pattern is not specific to CGNS.  Reviewers of this proposal report
that at least one widely used commercial post-processing format forces
the identical workaround: although it acquired high-order support, that
support remains restricted to nodal---and therefore continuous---values,
so discontinuous fields must be emitted either by duplicating geometry
or by writing each element as its own topologically independent region.
The same limitation is reported to have been a principal motivation for
CPEX~0045.  Two unrelated formats exhibiting the same defect indicates
that this is a general gap in how solution data is modelled, rather
than a CGNS-specific oversight, and it means CPEX~0045 and this
proposal are two approaches to one problem rather than competitors.

\subsection{Inadequacy of Existing CGNS Constructs}

No existing CGNS mechanism captures the shared/independent
distinction:

\begin{description}[leftmargin=2em]
\item[\texttt{GridLocation\_t}] specifies \emph{where} data is
  located (vertices, cell centers, faces, edges, interpolation
  points, or integration points), but not whether values at shared
  locations are shared or element-local.  A \texttt{Vertex}-located
  solution could use either layout; the same applies to
  \texttt{InterpolationPoints} and \texttt{IntegrationPoint}.

\item[\texttt{PointSet}] (\texttt{PointList}, \texttt{PointRange})
  can index subsets of data but does not encode DOF-sharing semantics.

\item[\texttt{InterpolationType\_t}] (CPEX~0045~\cite{cpex0045})
  describes the polynomial basis (e.g., Lagrange, monomial), but not
  whether that basis yields a globally shared or element-local DOF set.

\item[\texttt{SolutionInterpolation\_t}] (CPEX~0045, a child of
  \texttt{Family\_t}) records the interpolation type and control-point
  layout for a given basic element type; the polynomial orders are
  recorded separately in the \texttt{InterpolationOrders} child of
  \texttt{FlowSolution\_t}.  Neither carries DOF-sharing information.

\item[\texttt{ItgPointsStartOffset}] (CPEX~0047~\cite{cpex0047})
  gives the per-element starting offsets of integration-point data, which
  implies an element-local layout for that particular grid location, but
  says nothing about vertex-, edge-, or face-located DOFs and does not
  generalize to other grid locations.

\item[Data array size] together with \texttt{GridLocation\_t}
  \emph{does} determine the layout for every encoding legal before this
  CPEX, and it should be stated plainly that this is so: the SIDS
  \texttt{DataSize} formula admits exactly one layout at each grid
  location (Section~\ref{sec:legacy-inference} tabulates them), and it
  does so irrespective of element mix.  What the sizing rules cannot do
  is admit an element-local layout at a shared-entity grid location at
  all---that layout is not merely ambiguous, it is inexpressible.  The
  gap this CPEX addresses is therefore one of expressiveness, not of
  ambiguity; see Section~\ref{sec:prior-art}.
\end{description}

\subsection{Scope and Non-Goals}
\label{sec:scope}

This proposal is deliberately narrow.  Stating plainly what it does and
does not close is the clearest way to show that it neither overlaps
CPEX~0045 nor CPEX~0047.

\paragraph{What it closes.}  One gap: element-local solution DOFs at
positions coinciding with shared mesh vertices, with the shared-vertex
grid retained.  This is the case of
Section~\ref{sec:field-evidence}, it has no conforming encoding today,
and it is not restricted to high-order methods---DG $p=1$ on a linear
mesh is the most common instance, and the predefined element types
extend the same pattern through fourth order.  Because the affected
node is \texttt{FlowSolution\_t} (and its \texttt{DiscreteData\_t},
\texttt{ZoneSubRegion\_t}, and \texttt{UserDefinedData\_t}
counterparts), the designator belongs there rather than inside the
higher-order interpolation infrastructure.

\paragraph{What it does not close, by design.}

\begin{itemize}[leftmargin=2em]
\item \textbf{Nothing that is already determined.}  At
  \texttt{CellCenter}, under CPEX~0045's
  \texttt{InterpolationPoints}, and under CPEX~0047's
  \texttt{IntegrationPoint}, the layout follows from the grid location
  and the sizing rules.  Recording it there is permitted, and
  recommended for uniformity, but it resolves nothing and this
  proposal does not claim otherwise.
\item \textbf{Higher-order DOF identification.}  Establishing which
  DOFs of two adjacent elements correspond across a shared face---the
  general dof-relation---requires per-element index mapping and
  orientation conventions that this proposal does not supply.  For
  arbitrary interpolation points it cannot be done at all from the
  metadata CGNS currently defines
  (Section~\ref{sec:dofstorage-interp}).
\item \textbf{Smoothness order.}  Whether duplicated DOF values agree by
  construction \emph{is} recorded, by the separate
  \texttt{InterfaceContinuity} attribute of
  Section~\ref{sec:continuity}---it is a distinct property and not
  derivable from storage layout.  What remains out of scope is the
  \emph{order} of smoothness: $C^k$ for $k \geq 1$ is a property of the
  basis and belongs in CPEX~0045's interpolation metadata.
\item \textbf{Structured zones}, \texttt{NFACE\_n} sections, and
  vector-conforming space orientation
  (Sections~\ref{sec:ptlist-restrictions} and~\ref{sec:hdiv-hcurl}).
\end{itemize}

\paragraph{An acknowledged redundancy.}  For discontinuous Galerkin data
with $p \leq 4$ on a Lagrange basis there will be two conforming ways to
express the same field: the \texttt{Vertex} encoding defined here, and
CPEX~0045's \texttt{InterpolationPoints}.  This is stated plainly
because the cost is borne asymmetrically---writers gain a choice, while
readers wishing to interpret all conforming files must support both.
Tolerating alternative encodings of similar data is long-standing CGNS
practice, and it is what makes the standard easy to write against, but
it is a genuine burden on reader implementors and should not be
presented as free.

Two things limit the cost.  First, \textbf{CPEX~0045 is the recommended
route wherever it is available}: it needs no redundant index list, it
extends to any order, and it is the better mechanism where the DOF
positions are not the mesh vertices.  The encoding here is offered as
the lower-adoption-cost path, not the preferred one.  Second, a reader
that implements only CPEX~0045 is never \emph{wrong}---it is simply
unable to read files that chose the other encoding, and can say so
precisely, because the \texttt{DofStorage} node makes that choice
explicit rather than leaving it to be inferred.

\subsection{Prior Art: The DOF-Map Concept in ASCI-DMF / SAF}
\label{sec:prior-art}

The concept encoded by \texttt{DofStorage\_t} has well-established prior art in the
scientific data management literature.  The ASCI Data Model Framework (ASCI-DMF) and
its implementation in the Sets and Fields (SAF) library~\cite{miller2003} introduced the
\emph{dof-relation}: given a flat buffer of DOF values, the dof-relation enumerates for
each element which buffer indices are assigned to it.  When two adjacent elements refer to
the \emph{same} buffer index for a shared interface entity, that DOF is shared---this is
\texttt{DofStorage\_t = Shared} in the present proposal.  When each element refers to
\emph{different} buffer indices (each element owns its own slot), the DOFs are
independent---corresponding to \texttt{DofStorage\_t = Independent}.

Miller~\cite{miller2003} notes that for piecewise-linear coordinate fields the dof-relation
and the mesh connectivity (topo-relation) are one and the same array, and are consequently
``hopelessly confused'' in practice.  CGNS today is in exactly this position: it has no
dof-relation layer, so the only dof-map available to a solution at a shared-entity grid
location is the one implied by the \texttt{Elements\_t} connectivity.  This does not make
existing files ambiguous---a conforming file is unambiguous, because \texttt{GridLocation\_t}
together with the SIDS \texttt{DataSize} formula fixes the layout in every legal case
(Section~\ref{sec:legacy-inference} tabulates them).  The cost is expressiveness: because the
implied dof-map \emph{is} the connectivity, a solution whose DOFs are element-local cannot be
written at \texttt{Vertex}, \texttt{EdgeCenter}, or \texttt{FaceCenter} at all.  CPEX~0045
supplies an independent per-element dof-map for \texttt{InterpolationPoints}, and CPEX~0047
does so for \texttt{IntegrationPoint}; both are element-local by construction.  What remains
uncovered is element-local DOFs at \texttt{Vertex} on the predefined element types, where
\texttt{DofStorage\_t} serves as the discriminator that makes a second sizing both legal and
self-describing.

It is important to note that \texttt{DofStorage\_t} encodes only the \emph{coarsest} level
of DOF-map metadata---shared versus independent---which is sufficient for the vast majority
of post-processing and data-exchange use cases.  The full generality of a dof-relation
(arbitrary per-element index remapping, as required for quadratic or higher-order elements
whose mid-edge DOFs must be identified across elements) is the domain of
CPEX~0045~\cite{cpex0045} and CPEX~0047~\cite{cpex0047}.  These CPEXs are therefore
complementary layers of the same concept introduced in ASCI-DMF.

\subsection{Naming History}
\label{sec:naming-history}

This proposal has not yet been presented, so the document carries no revision history.  It
did, however, pass through two working names before this one, and both left traces that a
reader may encounter---hence this note.

An early draft used \texttt{SolutionRepresentation\_t}, which is where the former source
filename \texttt{CPEX-0050-solution-representation.tex} came from.  A later draft used
\texttt{SolutionContinuity\_t}, with values \texttt{Continuous} and
\texttt{Discontinuous}, and it is under that name that the CPEX registry currently lists
the entry (scope line ``Support Solution Continuity Type in CGNS,'' attachment
\texttt{CPEX-0050-SolutionContinuity.pdf}).  That vocabulary proved misleading: readers
consistently understood ``continuity'' as a claim about the mathematical smoothness of the
field, which this node does not make.

The name adopted here is \texttt{DofStorage\_t}, with values \texttt{DofStorageShared} and
\texttt{DofStorageIndependent}, chosen to state plainly that the node describes \emph{storage
layout}.  The source document and its PDF are named to match
(\texttt{CPEX-0050-dof-storage}).  \textbf{The registry entry requires a corresponding
update} to its scope line and attachment.  No files have been written with either earlier
name---there is no reference implementation yet---so no migration path is required.

\section{Detailed Description}
%% ═════════════════════════════════════════════════════════════════════════

\subsection{Design Overview}

The proposal introduces:

\begin{enumerate}[leftmargin=2em]
\item A new \texttt{DofStorage\_t} enumeration with values
  covering the common DOF storage layouts
  (Section~\ref{sec:enum}).
\item A new optional child node, \texttt{DofStorage}, of
  \texttt{FlowSolution\_t}, \texttt{DiscreteData\_t},
  \texttt{ZoneSubRegion\_t}, and \texttt{UserDefinedData\_t},
  recording the DOF storage layout
  (Section~\ref{sec:sids-node}).
\item One pair of position-based Mid-Level Library~\cite{cgns-mll}
  functions to read and
  write the DOF storage layout, following the pattern established by
  \texttt{cg\_gridlocation\_read} / \texttt{cg\_gridlocation\_write}
  (Sections~\ref{sec:mll} and~\ref{sec:mll-impl}).
\item A second, independent enumeration
  \texttt{InterfaceContinuity\_t} and its optional child node
  \texttt{InterfaceContinuity}, on the same four parents, recording
  whether duplicated DOFs represent a field that is continuous across
  element interfaces (Section~\ref{sec:continuity}).  This answers a
  different question from \texttt{DofStorage\_t} and is the one piece of
  information here that no other CGNS metadata can supply.
\item A second pair of position-based functions for that attribute,
  built on the same address-helper mechanism.
\item Fortran bindings for both pairs (Example~\ref{ex:fortran}).
\end{enumerate}

\subsection{New Enumeration: \texttt{DofStorage\_t}}
\label{sec:enum}

\begin{lstlisting}[language=C]
typedef enum {
  CGNS_ENUMV( DofStorageNull )        = CG_Null,
  CGNS_ENUMV( DofStorageUserDefined ) = CG_UserDefined,
  CGNS_ENUMV( DofStorageShared )                = 2,
  CGNS_ENUMV( DofStorageIndependent )           = 3
} CGNS_ENUMT( DofStorage_t );

#define NofValidDofStorage 4

extern CGNSDLL const char *DofStorageName[NofValidDofStorage];
\end{lstlisting}

The enumeration values are:

\begin{description}[leftmargin=2em]
\item[\texttt{DofStorageNull}] No DOF storage layout specified.
  This is the default for backward compatibility: existing
  files and codes that do not set this field are unaffected.
  See Section~\ref{sec:legacy-inference} for the recommended
  interpretation of legacy data.

\item[\texttt{DofStorageUserDefined}] Application-defined DOF storage
  layout not covered by the standard values.  When this value is
  used, writers \emph{shall} attach a \texttt{Descriptor\_t} child
  node named \texttt{"DofStorageDescription"} to the same parent
  node.  The string value identifies
  the storage convention (e.g.,
  \texttt{"HDG-trace"}, \texttt{"C1-spline"}).  This allows readers
  to recognize the convention without requiring a separate
  side-channel; see Example~\ref{ex:dispatch} for the reader side.

\item[\texttt{DofStorageShared}] DOFs at shared mesh entities
  (vertices, edges, faces) are \emph{shared} between adjacent
  elements: each shared entity carries exactly one value.  This is
  a statement about \emph{storage and DOF-sharing semantics}, not
  about the mathematical smoothness of the field.
  Typical of: Continuous Galerkin FEM,
  $C^0$ spectral element methods, isogeometric analysis with
  $C^0$~junctions.  See the caveat on vector-conforming spaces below.

\item[\texttt{DofStorageIndependent}] The solution field is
  element-local: each element owns independent DOFs, including at
  shared geometric locations, and no interface DOF is shared between
  adjacent elements.  Typical of: Discontinuous Galerkin methods,
  finite volume methods, $C^{-1}$ spectral element methods.
\end{description}

\subsubsection{Caveat: Vector-Conforming Spaces}
\label{sec:hdiv-hcurl}

$\boldsymbol{H}(\operatorname{div})$-conforming spaces
(e.g., Raviart--Thomas) and $\boldsymbol{H}(\operatorname{curl})$-conforming spaces
(e.g., N\'{e}d\'{e}lec) store one value per shared interface entity---a normal-flux
or tangential-component DOF, respectively---and so satisfy the letter of the
\texttt{DofStorageShared} definition, even though the full vector field is not
pointwise $C^0$-continuous.

However, such DOFs additionally carry a per-element \textbf{orientation
convention}: the sign of the stored value depends on a choice of outward
normal (\,$\boldsymbol{H}(\operatorname{div})$\,) or edge tangent direction
(\,$\boldsymbol{H}(\operatorname{curl})$\,), and adjacent elements see the same
DOF with opposite sign.  \texttt{DofStorage\_t} does not encode that
orientation, and no existing CGNS construct does either.

Accordingly:

\begin{itemize}[leftmargin=2em]
\item A writer \emph{may} label such a field \texttt{DofStorageShared}, since the
  storage statement is accurate.
\item A writer that does so \emph{shall} also mark the field with
  \texttt{DofStorageUserDefined}-style provenance---either by using
  \texttt{DofStorageUserDefined} with a
  \texttt{DofStorageDescription} of \texttt{"Hdiv-RT"} or
  \texttt{"Hcurl-Nedelec"}, or by attaching a
  \texttt{Descriptor\_t} identifying the space---so that readers are not
  misled.
\item A reader \emph{shall not} interpolate, average, or otherwise treat
  \texttt{DofStorageShared} DOFs as pointwise nodal values of a scalar field
  without first establishing that the field is nodal.  Applying nodal
  interpolation to Raviart--Thomas or N\'{e}d\'{e}lec DOFs yields
  incorrect results.
\end{itemize}

Supplying the orientation metadata that would make vector-conforming
spaces safely self-describing is deliberately out of scope for this
CPEX and is a natural subject for a future, narrowly scoped proposal.

\subsubsection{Rationale for Two-Value Classification}

The two values are not of equal weight, and the proposal is clearer for
saying so.

\texttt{DofStorageIndependent} is load-bearing: at
\texttt{GridLocation\_t = Vertex} it admits a layout that has no other
conforming encoding, and a reader must consult it to size and interpret
the field correctly (Section~\ref{sec:shared-vertex-layout}).

\texttt{DofStorageShared} is confirmatory.  Wherever it is valid, the sharing it
describes is already realized by the \texttt{Elements\_t} connectivity,
so a reader that ignores the node reaches the same conclusion.  It is
retained for three reasons: it makes the layout explicit rather than
implied, so files are self-describing; it gives writers a way to state
the layout positively instead of relying on the absence of
\texttt{DofStorageIndependent}; and an enumeration offering only one substantive
value would be an odd construct with no precedent in the SIDS.  It is
\emph{not} retained on the basis that readers require it, and
Section~\ref{sec:scope} should be read as limiting the claims made for
it.  In particular, \texttt{DofStorageShared} is meaningless at $p=0$ and invalid
on a volume \texttt{InterpolationPoints} block
(Section~\ref{sec:dofstorage-interp}).

With that asymmetry stated, methods that appear to require finer
distinctions are handled by the two values combined with standard
CGNS patterns:

\begin{description}[leftmargin=2em]
\item[HDG and mixed-layout methods] use both element-local volume DOFs
  and face-local trace DOFs.  Note that the trace space of the standard
  hybridizable formulation is \emph{not} globally continuous: it
  consists of face-wise polynomials with no continuity imposed between
  adjacent faces, so trace DOFs are generally discontinuous along
  skeleton edges and vertices.  \texttt{DofStorageShared} on a trace block
  therefore asserts only that the two volume elements adjacent to a
  given face index the same DOF block for that face---the reference
  entity set is the adjacent \emph{volume} elements, per
  Section~\ref{sec:dofstorage-interp}---and asserts nothing about
  continuity across the skeleton.  The two layouts are stored as
  separate \texttt{FlowSolution\_t} nodes, following the same pattern
  CGNS already uses to separate fields at different
  \texttt{GridLocation\_t} values.  A dedicated \texttt{MixedStorage}
  value would conflate two distinct data layouts into a single node,
  making it harder, not easier, for post-processors to interpret the
  data.

\item[Penalized / weakly-continuous DG methods] enforce continuity
  through penalty terms in the variational formulation, but the data
  layout remains element-local: each element owns its own DOFs.  The
  correct label is \texttt{DofStorageIndependent}.  ``Weak continuity''
  is a solver-internal property of the numerical method, not a property
  of the stored data that readers and post-processors need to act on.

\item[Isogeometric analysis ($C^k$, $k \geq 1$)] uses basis functions
  with higher-than-$C^0$ smoothness, but the data layout still
  shares DOFs at patch interfaces.  The
  correct label is \texttt{DofStorageShared}.  The smoothness order
  $k$ is a property of the basis, not of the data layout; it belongs in
  the interpolation metadata (CPEX~0045), not in the DOF storage type.
\end{description}

The \texttt{DofStorageUserDefined} value remains available
as an escape hatch, consistent with CGNS convention for all
enumeration types.

\textbf{Scope note.}  \texttt{DofStorage\_t} captures
\emph{storage and DOF-sharing semantics} only---it answers
``are interface DOFs shared or element-local?''  It does not
encode the polynomial basis, smoothness order, patch topology,
orientation conventions (Section~\ref{sec:hdiv-hcurl}), or
support-radius metadata that isogeometric analysis (IGA), meshless, or other
non-standard discretizations may additionally require.  Those
richer descriptions belong in CPEX~0045, CPEX~0047,
or in future extensions; this CPEX is intentionally
scoped to the coarser, universally applicable
shared/independent distinction.

\subsubsection{Enumeration Value Naming}
\label{sec:value-naming}

For every CGNS enumeration, the string written to the file is the
enumerator's own name; only the \texttt{Null} and \texttt{UserDefined}
members are stored in abbreviated form, as \texttt{"Null"} and
\texttt{"UserDefined"} (cf.\ \texttt{GridLocationNull} stored as
\texttt{"Null"}, while \texttt{Vertex} is stored as \texttt{"Vertex"}).
The choice of identifier is therefore also a choice of file-format
token, not merely a source-level one.

Two naming patterns are established in the SIDS.  Most enumerations use
bare domain-specific nouns---\texttt{Vertex}, \texttt{CellCenter},
\texttt{Kilogram}, \texttt{Structured}.  Where the bare word would be too
generic, however, CGNS prefixes it: every value of \texttt{BCType\_t}
carries a \texttt{BC} prefix (\texttt{BCWall}, \texttt{BCInflow},
\texttt{BCTunnelOutflow}) rather than risk \texttt{Wall} or
\texttt{Inflow} in the global namespace, and those prefixed names appear
on disk unchanged.

Both enumerations introduced here follow the second pattern, and for the
same reason.  \texttt{Shared}, \texttt{Independent},
\texttt{Continuous}, and \texttt{Discontinuous} are all generic
adjectives that applications and I/O layers commonly define for
unrelated purposes, and \texttt{cgnslib.h} injects enumeration values
into the global C namespace, so a collision would surface as a compile
error in downstream code.  The values are therefore
\texttt{DofStorageShared}, \texttt{DofStorageIndependent},
\texttt{InterfaceContinuous}, and \texttt{InterfaceDiscontinuous}, in
the C and Fortran bindings and on disk alike.  No collision exists in
\texttt{cgnslib.h} today; the prefix forecloses one.

Two points about this choice bear recording, because an earlier draft of
this proposal got the first of them wrong.

\textbf{It is a file-format decision, not a source-compatibility one.}
Because the stored token follows the identifier, the strings written to
disk are \texttt{"DofStorageShared"} and
\texttt{"DofStorageIndependent"}, not \texttt{"Shared"} and
\texttt{"Independent"}.  An earlier draft asserted that adopting the
prefixed forms ``would change only the C and Fortran identifiers, not the
on-disk strings.''  That was incorrect, and the mistake is worth naming
because it would have produced a library whose header and string table
disagreed---an interoperability failure rather than a stylistic one.

\textbf{It costs nothing now and would cost later.}  There is no
reference implementation and no file has been written with either
enumeration, so the prefix is free at the time of writing.  After
implementation it would require a migration path for both the C API and
the stored strings.  Settling it before implementation is the whole
reason for raising it here rather than deferring it.

The verbosity is the acknowledged cost: \texttt{DofStorageIndependent}
is longer than \texttt{Independent} both in source and in the file.
Given \texttt{BCWallViscousHeatFlux} as precedent this is within CGNS
norms, and the alternative---generic adjectives in a public header, or
one enumeration prefixed and its sibling bare---is worse on both
consistency and safety.

\subsection{New Enumeration: \texttt{InterfaceContinuity\_t}}
\label{sec:continuity}

\texttt{DofStorage\_t} records how DOFs are \emph{stored}.  It says
nothing about what the stored values \emph{mean} where storage is
duplicated, and that turns out to be the one property in this problem
space that no existing CGNS metadata can supply.

Consider two files that are identical in every respect CGNS can
currently express---same \texttt{GridLocation\_t}, same array length,
same CPEX~0045 basis and order, same element set, and both with
duplicated DOFs at element interfaces:

\begin{center}
\begin{tabular}{lll}
\toprule
& \textbf{Stored} & \textbf{Duplicated values at an interface} \\
\midrule
CG spectral element & per element & agree, by construction \\
Discontinuous Galerkin & per element & differ, meaningfully \\
\bottomrule
\end{tabular}
\end{center}

\noindent Nothing distinguishes them.  A post-processor must therefore
assume the worst case---that every interface carries a genuine
jump---and can never safely weld duplicated DOFs, average them, or
reconstruct a continuous field, even when the discretization guarantees
that doing so is exact.  An error estimator cannot separate a physical
jump from one that is zero by construction.  The information is not
derivable from the layout, because both files have the same layout.

\begin{lstlisting}[language=C]
typedef enum {
  CGNS_ENUMV( InterfaceContinuityNull )        = CG_Null,
  CGNS_ENUMV( InterfaceContinuityUserDefined ) = CG_UserDefined,
  CGNS_ENUMV( InterfaceContinuous )            = 2,
  CGNS_ENUMV( InterfaceDiscontinuous )         = 3
} CGNS_ENUMT( InterfaceContinuity_t );

#define NofValidInterfaceContinuity 4

extern CGNSDLL const char
    *InterfaceContinuityName[NofValidInterfaceContinuity];
\end{lstlisting}

\begin{description}[leftmargin=2em]
\item[\texttt{InterfaceContinuityNull}] Unspecified; the default, and
  the state of every file predating this CPEX.  A reader
  \emph{shall not} assume continuity from its absence: the safe
  interpretation is to preserve all duplicated values as distinct.

\item[\texttt{InterfaceContinuous}] Wherever storage duplicates a DOF at
  a shared geometric entity, all copies hold the same value, by
  construction of the discretization.  The duplication is redundancy,
  not information: a reader may weld, average, or interpolate across
  element interfaces without loss.

\item[\texttt{InterfaceDiscontinuous}] Duplicated values may differ, and
  the differences are meaningful.  Readers must not average or conflate
  them.  This is the expected value for DG, finite volume, and any
  method whose interface jumps carry physical or numerical content.

\item[\texttt{InterfaceContinuity\allowbreak UserDefined}] As with
  \texttt{DofStorageUserDefined}, writers \emph{shall} attach a
  \texttt{Descriptor\_t} child named
  \texttt{"InterfaceContinuity\allowbreak Description"} to the same
  parent.
\end{description}

\subsubsection{Relationship to \texttt{DofStorage\_t}}

The two attributes are orthogonal, and each combination has a meaning:

\begin{center}
\begin{tabular}{lll}
\toprule
& \textbf{\texttt{...Continuous}} & \textbf{\texttt{...Discontinuous}} \\
\midrule
\texttt{DofStorageShared}      & CG; redundant$^{\dagger}$ & inconsistent$^{\ddagger}$ \\
\texttt{DofStorageIndependent}\ & CG stored per element     & DG, FV, spectral $C^{-1}$ \\
\bottomrule
\end{tabular}
\end{center}

\noindent{\small $^{\dagger}$~Shared storage realizes continuity through
the connectivity itself, so the annotation adds nothing derivable.  It is
permitted for uniformity.}

\noindent{\small $^{\ddagger}$~Contradictory: a single shared slot cannot
hold two differing values.  \texttt{cgnscheck} should report an error
(Section~\ref{sec:cgnscheck}).}

The load-bearing cell is \texttt{DofStorageIndependent} + \texttt{InterfaceContinuous}: a
continuous field stored redundantly, which is exactly the CG
spectral-element case above and the case that motivates this attribute.
It is also the combination a reader most benefits from knowing, since it
is the only one in which welding is both safe and profitable.

\subsubsection{Scope of the Assertion}

Three limits are deliberate, and stating them is what keeps this
attribute narrow enough to be useful.

\textbf{It records agreement, not smoothness order.}
\texttt{InterfaceContinuous} asserts that duplicated DOFs coincide,
which for a nodal basis means the field is at least $C^0$ across the
interface.  It does not encode the smoothness order of the underlying
basis: $C^k$ for $k \geq 1$, as in isogeometric analysis, is a property
of the basis and belongs in CPEX~0045's interpolation metadata, exactly
as Section~\ref{sec:scope} states for the storage attribute.

\textbf{It is a writer's assertion, and the library does not verify it.}
The MLL shall not compare values on write; doing so would require
reading the field arrays and resolving the DOF correspondence, which for
arbitrary interpolation points is not generally possible
(Section~\ref{sec:dofstorage-interp}).  \texttt{cgnscheck} \emph{may}
sample duplicated DOFs numerically and warn on disagreement; see
Section~\ref{sec:cgnscheck}.  A writer that does not know shall write
nothing, leaving \texttt{InterfaceContinuityNull}.

\textbf{It is meaningful only where DOFs are duplicated.}  That is:
under \texttt{DofStorage\_t = Independent}, under
\texttt{GridLocation\_t = InterpolationPoints} and
\texttt{IntegrationPoint}, and under the \texttt{Vertex} plus
\texttt{PointList} encoding of
Section~\ref{sec:shared-vertex-layout}.  Where no duplication occurs---a
\texttt{CellCenter} solution, or genuinely shared vertex storage---the
attribute is vacuous rather than wrong, and writers may omit it.

\subsubsection{Node Placement Rationale}

The node is placed as a child of \texttt{FlowSolution\_t} (rather
than, for example, \texttt{Zone\_t}) because:

\begin{itemize}[leftmargin=2em]
\item The DOF storage layout is a property of the \emph{solution field},
  not of the mesh or the zone.

\item A single zone may contain multiple \texttt{FlowSolution\_t}
  nodes with different layouts---for example, an HDG solver
  storing both volume (independent) and trace (shared) solutions,
  or a multi-physics code storing a shared-DOF displacement field
  alongside an independent-DOF stress field.

\item This parallels the existing \texttt{GridLocation\_t} child of
  \texttt{FlowSolution\_t}, which is also a per-solution-node
  property.

\item Placing it within CPEX~0045's \texttt{SolutionInterpolation\_t}
  would be doubly wrong: that node is a child of \texttt{Family\_t},
  so a per-family setting could not distinguish two solutions on the
  same family, and it would incorrectly limit the scope to
  higher-order solutions when the distinction applies at any order.
\end{itemize}

\subsubsection{Why a New Node Rather Than a New \texttt{GridLocation\_t} Value}
\label{sec:why-new-node}

The most obvious alternative is to add a \texttt{GridLocation\_t}
value---say \texttt{ElementVertex}---meaning ``at element-local copies
of the vertices.''  This proposal rejects that approach:

\begin{itemize}[leftmargin=2em]
\item \textbf{It conflates two orthogonal axes.}  \texttt{GridLocation\_t}
  answers \emph{where}; DOF storage answers \emph{how many copies}.  Each
  of the seven existing spatial locations can in principle carry either
  layout, so folding the second axis into the first would require
  roughly doubling the enumeration (\texttt{ElementVertex},
  \texttt{ElementEdgeCenter}, \texttt{ElementFaceCenter}, \dots) rather
  than adding one value.

\item \textbf{It would not be backward compatible in practice.}
  \texttt{GridLocation\_t} is consumed by essentially every CGNS reader,
  and each has a switch over its values.  A new value causes existing
  readers to fail or fall through to a default, whereas an unknown
  \emph{child node} is silently ignored by both the MLL and
  \texttt{cgnscheck} (Section~\ref{sec:compat}).

\item \textbf{The distinction is not always locational.}  For
  \texttt{CellCenter} data the layout is independent with no
  corresponding ``element-local'' location to name; the flag still
  carries useful information for coupling frameworks.

\item \textbf{Precedent.}  CGNS already separates orthogonal per-solution
  properties into sibling child nodes (\texttt{GridLocation},
  \texttt{Rind}, \texttt{DataClass}, \texttt{DimensionalUnits}) rather
  than encoding them in a single enumeration.
\end{itemize}

Note that CPEX~0045 and CPEX~0047 do each add a
\texttt{GridLocation\_t} value (\texttt{InterpolationPoints} and
\texttt{IntegrationPoint}); those additions describe genuinely new
\emph{locations}, which is the correct use of that enumeration.

\subsection{New MLL Functions}
\label{sec:mll}

\subsubsection{Design: Position-Based API}

The API follows the pattern CGNS uses for every other optional scalar
metadata child---\texttt{GridLocation}, \texttt{DataClass},
\texttt{Rind}, \texttt{DimensionalUnits}, \texttt{Descriptor}: a single
function pair that operates on the node at the current position, set by
\texttt{cg\_goto}, backed by an internal
\texttt{cgi\_\textit{x}\_address()} helper that resolves the current
position to the relevant struct field and enumerates the legal parent
labels.

This is preferred over a family of explicit-index functions --- one per
parent node type, in the style of

\begin{quote}
\texttt{cg\_sol\_dof\_storage\_write(fn,B,Z,S,type)} \\
\texttt{cg\_discrete\_dof\_storage\_write(fn,B,Z,D,type)} \\
\texttt{cg\_subreg\_dof\_storage\_write(fn,B,Z,SR,type)}
\end{quote}

\noindent plus matching readers and Fortran bindings --- because:

\begin{itemize}[leftmargin=2em]
\item Two C functions and two Fortran functions cover all four parent
  node types, instead of six and six.
\item Adding a fifth permitted parent later requires one line in the
  address helper, not two new public functions plus Fortran bindings.
\item The address helper locates an existing child \emph{by label}
  (Section~\ref{sec:address}), so no node identifier needs to be cached
  in the internal structures.  This removes a field from three structs
  and eliminates a class of overwrite bug.
\item It matches what users already do for the sibling property:
  \texttt{cg\_goto(...); cg\_gridlocation\_write(CellCenter);}
\end{itemize}

\subsubsection{C API}

\begin{lstlisting}[language=C]
/*
 * Write the DOF storage layout of the node at the current position,
 * which must have been set by cg_goto()/cg_gopath().
 *
 * Valid parent labels: FlowSolution_t, DiscreteData_t,
 *                      ZoneSubRegion_t, UserDefinedData_t.
 *
 * DofStorage - DofStorage_t value.  Writing DofStorageNull removes
 *              an existing DofStorage child, restoring the
 *              "unspecified" state.
 *
 * Returns CG_OK, or CG_ERROR / CG_INCORRECT_PATH on failure.
 */
CGNSDLL int cg_dof_storage_write(
    CGNS_ENUMT(DofStorage_t) DofStorage);

/*
 * Read the DOF storage layout of the node at the current position.
 *
 * DofStorage - [out] DofStorage_t value.  Set to DofStorageNull,
 *              with a CG_OK return, when the node has no
 *              DofStorage child (legacy file or unset).
 *
 * Returns CG_OK, or CG_ERROR / CG_INCORRECT_PATH on failure.
 */
CGNSDLL int cg_dof_storage_read(
    CGNS_ENUMT(DofStorage_t) *DofStorage);

/*
 * Write / read the interface continuity of the node at the current
 * position.  Parent labels, overwrite behaviour, and the meaning of
 * the Null value are exactly as for cg_dof_storage_write/read: writing
 * InterfaceContinuityNull removes an existing child, and reading a
 * node that has none yields InterfaceContinuityNull with CG_OK.
 *
 * The library does not validate the assertion against the field data.
 */
CGNSDLL int cg_interface_continuity_write(
    CGNS_ENUMT(InterfaceContinuity_t) InterfaceContinuity);

CGNSDLL int cg_interface_continuity_read(
    CGNS_ENUMT(InterfaceContinuity_t) *InterfaceContinuity);

/*
 * Return the string name for a DofStorage_t value.
 * Matches the convention of cg_GridLocationName, cg_DataTypeName.
 * Returns NULL for out-of-range values.
 */
CGNSDLL const char *cg_DofStorageName(
    CGNS_ENUMT(DofStorage_t) type);
\end{lstlisting}

\textbf{Behavior:}

\begin{itemize}[leftmargin=2em]
\item \texttt{cg\_dof\_storage\_write} creates the
  \texttt{DofStorage} child node under the node at the current
  position.  In \texttt{CG\_MODE\_MODIFY}, an existing
  \texttt{DofStorage} child is deleted first.  Writing
  \texttt{DofStorageNull} deletes an existing child without creating a
  replacement.

\item \texttt{cg\_dof\_storage\_read} returns the value cached in the
  internal structure by the tree parser.  If the node does not exist
  (legacy file or unset), it returns \texttt{CG\_OK} with
  \texttt{DofStorageNull}, never an error.

\item Both functions return \texttt{CG\_INCORRECT\_PATH} if the current
  position is not one of the four permitted parent labels, matching
  \texttt{cg\_gridlocation\_read}/\texttt{\_write} behavior.
\end{itemize}

\subsection{Internal Data Structure Changes}

Four structures in \texttt{cgns\_header.h} each gain one field:
\texttt{cgns\_sol} (for \texttt{FlowSolution\_t}),
\texttt{cgns\_discrete} (for \texttt{DiscreteData\_t}),
\texttt{cgns\_subreg} (for \texttt{ZoneSubRegion\_t}), and
\texttt{cgns\_user\_data} (for \texttt{UserDefinedData\_t}).

\begin{lstlisting}[language=C]
typedef struct {            /* FlowSolution_t node */
    /* ... existing fields ... */

    /* CPEX 0050 */
    CGNS_ENUMT(DofStorage_t) dof_storage;
} cgns_sol;

/* cgns_discrete, cgns_subreg, and cgns_user_data gain the
 * identically named and typed field. */
\end{lstlisting}

The \texttt{dof\_storage} field defaults to
\texttt{DofStorageNull} (value~0), which is both the
zero-initialization value and the ``not specified'' state.

No node-identifier field is required.  The write path locates an
existing child by label at write time (Section~\ref{sec:address}),
exactly as \texttt{cgi\_location\_address} does for
\texttt{GridLocation\_t}.  This mirrors the existing structures, which
carry \texttt{location} but no \texttt{location\_id}.

\subsection{Internal Lookup Table and String Mapping}

The string table must be defined in \texttt{cgnslib.c} alongside
\texttt{GridLocationName} and its siblings:

\begin{lstlisting}[language=C]
const char *DofStorageName[NofValidDofStorage] = {
    "Null",
    "UserDefined",
    "DofStorageShared",
    "DofStorageIndependent"
};
\end{lstlisting}

A string-to-enum helper is added to \texttt{cgns\_internals.c},
following \texttt{cgi\_GridLocation} exactly.  That includes its
forward-compatibility behavior: an unrecognized string in a file
written by a \emph{newer} library version degrades to
\texttt{UserDefined} with a warning rather than failing.

\begin{lstlisting}[language=C]
int cgi_DofStorage(char *Name, CGNS_ENUMT(DofStorage_t) *type)
{
    int i;
    for (i = 0; i < NofValidDofStorage; i++) {
        if (strcmp(Name, DofStorageName[i]) == 0) {
            (*type) = (CGNS_ENUMV(DofStorage_t))i;
            return CG_OK;
        }
    }
    if (cg->version > CGNSLibVersion) {
        (*type) = CGNS_ENUMV(DofStorageUserDefined);
        cgi_warning("Unrecognized DofStorage Type '%s' "
                    "replaced with 'UserDefined'", Name);
        return CG_OK;
    }
    cgi_error("Unrecognized DofStorage: %s", Name);
    return CG_ERROR;
}
\end{lstlisting}

\subsection{MLL Implementation Requirements}
\label{sec:mll-impl}

Throughout this section, \texttt{cg} is the file-scope
current-file pointer used internally by \texttt{cgnslib.c}, and
\texttt{posit} is the file-scope current-position record maintained by
\texttt{cg\_goto}.  Neither is declared in the listings, matching the
surrounding library code.

\subsubsection{Address Resolution Function (\texttt{cgns\_internals.c})}
\label{sec:address}

\begin{lstlisting}[language=C]
CGNS_ENUMT(DofStorage_t) *cgi_dof_storage_address(
    int local_mode, int *ier)
{
    double *id, parent_id;
    CGNS_ENUMT(DofStorage_t) *dof_storage = 0;
    int nnod;

    if (posit == 0) {
        cgi_error("No current position set by cg_goto\n");
        (*ier) = CG_ERROR;
        return CG_OK;
    }

    /* Possible parents for DofStorage_t: FlowSolution_t,
     * DiscreteData_t, ZoneSubRegion_t, UserDefinedData_t */
    if (strcmp(posit->label, "FlowSolution_t") == 0)
        ADDRESS4SINGLE_ALLOC(cgns_sol, dof_storage)
    else if (strcmp(posit->label, "DiscreteData_t") == 0)
        ADDRESS4SINGLE_ALLOC(cgns_discrete, dof_storage)
    else if (strcmp(posit->label, "ZoneSubRegion_t") == 0)
        ADDRESS4SINGLE_ALLOC(cgns_subreg, dof_storage)
    else if (strcmp(posit->label, "UserDefinedData_t") == 0)
        ADDRESS4SINGLE_ALLOC(cgns_user_data, dof_storage)
    else {
        cgi_error("DofStorage_t node not supported under "
                  "'%s' type node", posit->label);
        (*ier) = CG_INCORRECT_PATH;
        return CG_OK;
    }

    /* On modify, delete any existing child, located by label */
    if (cg->mode == CG_MODE_MODIFY &&
        local_mode == CG_MODE_WRITE) {
        if (cgi_get_nodes(parent_id, "DofStorage_t", &nnod, &id))
            return CG_OK;
        if (nnod > 0) {
            if (cgi_delete_node(parent_id, id[0])) {
                (*ier) = CG_ERROR;
                return CG_OK;
            }
            CGNS_FREE(id);
        }
    }
    return dof_storage;
}
\end{lstlisting}

Locating the existing child by label is what makes a cached node
identifier unnecessary, and is why the overwrite path cannot create a
duplicate child.

\subsubsection{Internal Tree Parser Update (\texttt{cgns\_internals.c})}

When a CGNS file is opened, the MLL tree parser
crawls the HDF5/CGIO tree and populates
internal C structures.  The parser must be updated to recognize child
nodes with label \texttt{DofStorage\_t} during the
traversal of \texttt{FlowSolution\_t} (\texttt{cgi\_read\_sol}),
\texttt{DiscreteData\_t} (\texttt{cgi\_read\_discrete}),
\texttt{ZoneSubRegion\_t} (\texttt{cgi\_read\_subregion}), and
\texttt{UserDefinedData\_t} (\texttt{cgi\_read\_user\_data}).

The required behavior is:

\begin{enumerate}[leftmargin=2em]
\item During memory allocation of the parent structure, the
  \texttt{dof\_storage} field is zero-initialized, which corresponds
  to \texttt{DofStorageNull}.
\item During the child-node traversal, if a child with label
  \texttt{"DofStorage\_t"} is found, read its C1 string
  data and map it to the enum value via
  \texttt{cgi\_DofStorage(string\_data, \&dof\_storage)}.
\item If no such child node exists, the field retains its default
  \texttt{DofStorageNull} value.
\end{enumerate}

This follows the existing pattern used for \texttt{GridLocation\_t}
parsing in \texttt{cgi\_read\_sol}.  No node identifier is stored;
see Section~\ref{sec:address}.

\subsubsection{Read Function Implementation}

\begin{lstlisting}[language=C]
int cg_dof_storage_read(CGNS_ENUMT(DofStorage_t) *DofStorage)
{
    CGNS_ENUMT(DofStorage_t) *dof_storage;
    int ier = 0;

    CHECK_FILE_OPEN

    if (cgi_check_mode(cg->filename, cg->mode, CG_MODE_READ))
        return CG_ERROR;

    dof_storage = cgi_dof_storage_address(CG_MODE_READ, &ier);
    if (dof_storage == 0) return ier;

    (*DofStorage) = (*dof_storage);
    return CG_OK;
}
\end{lstlisting}

Because the tree parser already handles the absent-node case by leaving
the field at \texttt{DofStorageNull}, the read function simply returns
the cached value and \texttt{CG\_OK}.  This avoids any need to intercept
\texttt{CG\_NODE\_NOT\_FOUND} at read time: the absent-node case is
handled once during file open, and all subsequent reads are served from
the in-memory cache.  Legacy code that iterates over solutions and
queries the DOF storage layout will always receive \texttt{CG\_OK} with
\texttt{DofStorageNull} for files that predate this CPEX.

\subsubsection{Write Function Implementation}

\begin{lstlisting}[language=C]
int cg_dof_storage_write(CGNS_ENUMT(DofStorage_t) DofStorage)
{
    CGNS_ENUMT(DofStorage_t) *dof_storage;
    int ier = 0;
    cgsize_t dim_vals;
    double posit_id, dummy_id;

    CHECK_FILE_OPEN

    if (cgi_check_mode(cg->filename, cg->mode, CG_MODE_WRITE))
        return CG_ERROR;

    if (INVALID_ENUM(DofStorage, NofValidDofStorage)) {
        cgi_error("Invalid DofStorage value: %d", (int)DofStorage);
        return CG_ERROR;
    }

    /* Resolves the parent, and on modify deletes any
     * existing DofStorage child (located by label). */
    dof_storage = cgi_dof_storage_address(CG_MODE_WRITE, &ier);
    if (dof_storage == 0) return ier;

    (*dof_storage) = DofStorage;

    /* Null means "unspecified": record nothing on disk.  Any
     * pre-existing child was removed by the address helper. */
    if (DofStorage == CGNS_ENUMV(DofStorageNull)) return CG_OK;

    if (cgi_posit_id(&posit_id)) return CG_ERROR;
    dim_vals = (cgsize_t)strlen(DofStorageName[DofStorage]);
    if (cgi_new_node(posit_id, "DofStorage", "DofStorage_t",
            &dummy_id, "C1", 1, &dim_vals,
            (void *)DofStorageName[DofStorage]))
        return CG_ERROR;

    return CG_OK;
}
\end{lstlisting}

Two details are worth noting.  First, validation uses the library's own
\texttt{INVALID\_ENUM(E,EMAX)} macro from \texttt{cgns\_header.h}, as
\texttt{cg\_gridlocation\_write} does, rather than an open-coded
\texttt{switch}.  Second, no node identifier is stored after
\texttt{cgi\_new\_node} returns, because the address helper will find
the node by label on any subsequent write.

\subsection{Data Layout for Independent DOFs at Shared Mesh Vertices}
\label{sec:shared-vertex-layout}

A common and important case arises when a DG solver uses a mesh whose
vertices are shared in the standard CGNS sense---enabling mesh walking,
stream tracing, and connectivity queries via the standard
\texttt{Elements\_t} tables---but stores element-local, independent
solution values at each element's copy of those vertices.  At a shared
vertex adjacent to $k$ elements there are $k$ distinct solution values,
one per element; readers must not average or conflate them.

The correct CGNS encoding for this pattern is
\texttt{GridLocation\_t = Vertex} combined with
\texttt{DofStorage\_t = Independent} and a
\texttt{PointList} that lists every element-vertex pair explicitly
(repeated vertex indices are expected and meaningful).  The
\texttt{DofStorage\_t} node is the machine-readable flag that
tells readers these repeated entries represent independent DOFs, not
duplicate data.

Without the \texttt{DofStorage\_t} node, a reader cannot
distinguish this layout from a malformed shared-DOF solution with
duplicate entries, which is why the node is necessary.  With it, a
post-processor or coupling framework can correctly:

\begin{itemize}[leftmargin=2em]
\item walk the mesh using the shared-vertex connectivity for geometry
  operations (stream tracing, surface intersection, etc.);
\item read solution values element-locally, preserving the jumps at
  shared interfaces.
\end{itemize}

\subsubsection{Applicability and Restrictions}
\label{sec:ptlist-restrictions}

This encoding is subject to the following restrictions, which the
SIDS amendment in Section~\ref{sec:sids-impact} makes normative.

\textbf{Unstructured zones only.}  The DOF ordering is defined by
traversal of the zone's \texttt{Elements\_t} sections, which structured
zones do not have.  The encoding is therefore valid only for
\texttt{ZoneType\_t = Unstructured}.  Structured zones have no way to
express independent DOFs at shared vertices, and this CPEX does not
add one.  A structured solver with element-local DOFs should either
store cell-centered data (\texttt{GridLocation\_t = CellCenter}, which
is unambiguously independent) or convert the affected region to an
unstructured zone.  Note that CPEX~0045's \texttt{InterpolationOrders}
child is likewise ``recognized only for \texttt{Unstructured}
zones,'' so the high-order route is not a structured fallback either.

\textbf{The \texttt{PointList} must cover every element of the zone.}
The ordering rule below is a traversal of the zone's elements; a
\texttt{PointList} covering only some elements has no defined anchor
into that traversal.  A partial-coverage independent solution should
use \texttt{GridLocation\_t = InterpolationPoints} (CPEX~0045) or
\texttt{IntegrationPoint} (CPEX~0047), both of which carry explicit
per-element element-index lists.

\textbf{Element type support.}  Fixed-size element types and
\texttt{MIXED} and \texttt{NGON\_n} sections are supported.
\texttt{NFACE\_n} is \emph{not}: a polyhedral element's vertices are
defined only indirectly, through its constituent faces, and CGNS
defines no canonical vertex ordering for such an element, so ``the
element's vertices in order'' is not well defined.  Zones containing
\texttt{NFACE\_n} sections must use
\texttt{GridLocation\_t = InterpolationPoints} or
\texttt{IntegrationPoint} for independent DOFs.

\textbf{\texttt{Rind\_t} must not be combined with this encoding.}
The \texttt{PointList} already enumerates every DOF explicitly, so
there is no separate rind extent to declare, and the SIDS defines no
ordering for rind entries within a point set.  \texttt{Rind\_t}
remains fully usable with \texttt{DofStorage\_t = Independent} when no
point set is present; see Section~\ref{sec:rind-interaction}.

\textbf{Storage overhead.}  Because the \texttt{PointList} is, by
construction, the concatenation of the zone's element connectivity, it
duplicates data already present in the \texttt{Elements\_t} sections at
a cost of one \texttt{cgsize\_t} per DOF.  This is exactly the
conflation of dof-relation and topo-relation that
Miller~\cite{miller2003} describes.  The overhead should be weighed
honestly against the two alternatives.

Writing the solution at \texttt{InterpolationPoints} instead does
\emph{not} destroy the shared-vertex connectivity:
\texttt{GridCoordinates\_t} and \texttt{Elements\_t} are untouched, and
mesh walking continues to work.  On capability alone, therefore, the
0045 route also satisfies the requirement of
Section~\ref{sec:field-evidence}, and this proposal should not claim
otherwise.  What it offers over that route is a far smaller
implementation burden for readers---no \texttt{Family\_t}-level
\texttt{SolutionInterpolation\_t} lookup, no basis evaluation, no
control-point machinery---for the common case in which the DOF
positions simply \emph{are} the mesh vertices.  For first-order DG that
distinction is the difference between reading one extra scalar node and
implementing an interpolation framework.

The alternative actually observed in production, by contrast, is
strictly worse than either: duplicating the grid coordinates
(Section~\ref{sec:field-evidence}) inflates
\texttt{GridCoordinates\_t} by the average vertex valence---far more
than one \texttt{cgsize\_t} per DOF---and destroys the connectivity
outright.  Measured against that, the \texttt{PointList} redundancy is
a substantial improvement.

Where CPEX~0045 or CPEX~0047 has been adopted and the DOF positions are
not the mesh vertices, \texttt{InterpolationPoints} or
\texttt{IntegrationPoint} remains the preferred encoding: both size the
array from per-element DOF counts with no redundant index list.  It
should also be acknowledged that community feedback has objected to
\emph{existing} cases where an identity point set must be written
purely as indirection; the redundancy here is a real cost to weigh, not
a formality.

\subsubsection{Other Grid Locations}

For element-local DOFs at non-vertex positions (interior quadrature
points, face quadrature points, etc.) under \texttt{FlowSolution\_t},
use \texttt{GridLocation\_t = InterpolationPoints} with CPEX~0045
metadata, or \texttt{GridLocation\_t = IntegrationPoint} with CPEX~0047
metadata.  Both are restricted by their respective proposals:
CPEX~0045 states that \texttt{InterpolationPoints} ``is valid only on
\texttt{FlowSolution\_t} nodes,'' and CPEX~0047 permits
\texttt{IntegrationPoint} under \texttt{FlowSolution\_t},
\texttt{ZoneSubRegion\_t}, \texttt{BC\_t}, and
\texttt{BCDataSet\_t}.  Consequently \texttt{DiscreteData\_t} has no
standard encoding for element-local DOFs at non-vertex positions;
\texttt{DofStorage\_t = Independent} on a \texttt{DiscreteData\_t} node
is meaningful for \texttt{CellCenter} data, and for vertex data under
the \texttt{PointList} encoding above, but not otherwise.  Closing
that gap is out of scope here.

\texttt{GridLocation\_t = Vertex} with a \texttt{PointList} is
specifically the correct choice when the DOF positions coincide with
mesh vertices and the shared-vertex mesh connectivity is to be
preserved.

\texttt{GridLocation\_t = Vertex} with \texttt{DofStorageIndependent}
and \emph{no} \texttt{PointList} is not valid: the SIDS
\texttt{DataSize} formula for \texttt{Vertex} yields
$\texttt{DataSize} = \texttt{VertexSize}$ (the shared-vertex count),
which cannot represent the larger element-local DOF count.
Similarly, \texttt{PointRange} is not suitable for this case because
a contiguous range of vertex indices cannot express the element-local
repetition of shared vertices; only \texttt{PointList} provides the
necessary per-element DOF ordering.
\texttt{GridLocation\_t = CellCenter} with \texttt{DofStorageIndependent}
remains valid since cell-centered data is inherently one value per
element with no shared-entity ambiguity.

\subsubsection{DOF Ordering Rule}
\label{sec:ordering-rule}

\textbf{SIDS Amendment ---
\texttt{PointList} semantics for independent DOFs.}
When \texttt{DofStorage\_t} is \texttt{DofStorageIndependent} and a
\texttt{PointList} is present, with
\texttt{GridLocation\_t = Vertex}, under any of
\texttt{FlowSolution\_t}, \texttt{DiscreteData\_t},
\texttt{ZoneSubRegion\_t}, or \texttt{UserDefinedData\_t},
repeated vertex indices are
permitted and represent element-local DOFs.  Solution array position
$i$ corresponds to the $i$-th entry of the \texttt{PointList}, and the
\texttt{PointList} shall be constructed as follows:

\begin{enumerate}[leftmargin=2em]
\item Traverse the zone's elements in ascending \textbf{element index}
  order.  Element indices are the global, zone-wide indices defined by
  each \texttt{Elements\_t} section's \texttt{ElementRange}; they are
  \emph{not} the section storage order, and sections are not required
  to be stored in ascending \texttt{ElementRange} order.

\item Within each element, list the element's vertex indices in the
  canonical vertex order defined for its element type in
  SIDS~\S7.3.

\item For \texttt{MIXED} sections, the element-type code that precedes
  each element's vertex list in the connectivity array is not a DOF and
  is not listed.

\item For \texttt{NGON\_n} sections, list the face's vertex indices in
  connectivity order; the per-element vertex count varies and the
  \texttt{PointList} length is the sum over all elements.
\end{enumerate}

Repeated indices under \texttt{DofStorage\_t = Shared},
\texttt{DofStorageUserDefined}, or \texttt{DofStorageNull} remain
undefined and invalid.  This amendment does not affect
\texttt{PointList} semantics under any other condition.

Because the \texttt{PointList} must equal the traversal above, a
validator can check it exactly against the \texttt{Elements\_t}
connectivity; see Section~\ref{sec:cgnscheck}.

See Example~\ref{ex:shared-vertex-dg} for the complete C encoding
of this pattern.

\subsection{Interaction with \texttt{Rind\_t} (Ghost Layers)}
\label{sec:rind-interaction}

When no point set is present, \texttt{DofStorage\_t} applies uniformly
to the entire solution field, including any rind (ghost) entries
declared by \texttt{Rind\_t}.  An \texttt{DofStorageIndependent} label means that
all data entries---interior and rind alike---are element-local: each
rind entry belongs to one element and must not be interpreted as a
shared vertex value.  DG solvers that use ghost layers for MPI halo
exchange may therefore store element-local rind DOFs in the standard
way; the \texttt{DofStorageIndependent} label covers them.  Rind
entries of a \texttt{DofStorageShared} solution retain their usual
shared-DOF semantics.  No special treatment of the rind is required
beyond what \texttt{Rind\_t} already specifies; the DOF storage label
is consistent across the full data array.

As stated in Section~\ref{sec:ptlist-restrictions}, \texttt{Rind\_t}
must not be combined with the \texttt{Vertex} + \texttt{DofStorageIndependent} +
\texttt{PointList} encoding, because the SIDS defines no position for
rind entries within a point set.

\section{Interaction with CPEX 0045 (Higher-Order Elements)}
%% ═════════════════════════════════════════════════════════════════════════

CPEX~0045~\cite{cpex0045} introduced
\texttt{GridLocation\_t = InterpolationPoints}, the
\texttt{InterpolationOrders} and \texttt{CharacteristicLength} children
of \texttt{FlowSolution\_t}, and the
\texttt{SolutionInterpolation\_t} and \texttt{ElementInterpolation\_t}
children of \texttt{Family\_t}.  The present CPEX complements rather
than modifies that infrastructure:

\begin{itemize}[leftmargin=2em]
\item CPEX~0045 answers: ``What polynomial basis and order describes
  the solution within each element?''
\item This CPEX answers: ``Are the resulting DOFs shared across element
  interfaces or element-local?''
\end{itemize}

Both pieces of metadata are needed for a complete description of a
higher-order solution field.  They are orthogonal:

\begin{center}
\begin{tabular}{lcc}
\toprule
& \textbf{Shared} & \textbf{Independent} \\
\midrule
Lagrange $p=1$ & CG FEM$^{\ddagger}$ & DG $p=1$ \\
Lagrange $p=3$ & CG spectral$^{\ddagger}$ & DG spectral \\
Hierarchical $p=2$ & n/a$^{\S}$ & DG (modal) \\
$p=0$ (constant) & n/a$^{\dagger}$ & FV / DG $p=0$ \\
\bottomrule
\end{tabular}
\end{center}

\noindent{\small $^{\dagger}$~A $p=0$ basis has no interface DOFs to
share: its single per-element DOF has no geometric support on the
element boundary.  \texttt{DofStorageShared} is therefore not merely unusual at
$p=0$ but meaningless, and \texttt{cgnscheck} should warn on it
(Section~\ref{sec:cgnscheck}).}

\noindent{\small $^{\ddagger}$~Realizable only at
\texttt{GridLocation\_t = Vertex} on the predefined element types,
where the \texttt{Elements\_t} connectivity supplies the DOF
identification.  It is \emph{not} realizable under
\texttt{InterpolationPoints}, where \texttt{DofStorageShared} is invalid on a
volume block (Section~\ref{sec:dofstorage-interp}).  Since predefined
element types reach only fourth order, shared storage is expressible
only for $p \leq 4$.}

\noindent{\small $^{\S}$~Hierarchical bases admitting a
vertex/edge/face/interior mode decomposition support continuous
assembly mathematically, but CPEX~0045's monomial encodings
(\texttt{ParametricMonomialsPascal}, \texttt{CartesianMonomialsPascal})
store modal coefficients that have no geometric support on any
sub-entity, and 0045 fixes no sub-entity ordering for them.  There is
consequently no entity to share and no DOF correspondence to
establish, so \texttt{DofStorageShared} cannot be acted upon.  The same holds for
\texttt{ParametricLagrange} with user-supplied control points: 0045
guarantees a principal-vertices-first ordering only for
\texttt{ElementInterpolation\_t}, not for
\texttt{SolutionInterpolation\_t}, and defines no orientation-aware
correspondence between the points of two adjacent elements.}

\subsection{Recommended Practice}

For higher-order solutions using \texttt{GridLocation\_t =
InterpolationPoints}:

\begin{enumerate}[leftmargin=2em]
\item Use CPEX~0045 to define the element type, interpolation basis,
  and polynomial order via \texttt{SolutionInterpolation\_t} on the
  \texttt{Family\_t} and \texttt{InterpolationOrders} on the
  \texttt{FlowSolution\_t}.
\item Use this CPEX to set \texttt{DofStorage\_t} on the
  \texttt{FlowSolution\_t} node.
\end{enumerate}

Example~\ref{ex:dg-write} shows both steps.

For lower-order solutions using \texttt{GridLocation\_t = Vertex} or
\texttt{CellCenter}, this CPEX can be used independently of CPEX~0045;
see Example~\ref{ex:cg-write}.
See Section~\ref{sec:shared-vertex-layout} for the prescribed data
layout when independent DOFs coincide with shared mesh vertices.

\subsection{\texttt{DofStorage\_t} Under \texttt{InterpolationPoints}}
\label{sec:dofstorage-interp}

Under \texttt{GridLocation\_t = InterpolationPoints}, CPEX~0045
defines the field-array length as
\[
  L \;=\; \sum_{e \in \mathcal{E}} N_{\mathrm{DOFs}}(e),
\]
where $\mathcal{E}$ is the set of elements covered by the block---all
zone elements when no \texttt{PointRange}/\texttt{PointList} is
present, or the listed elements otherwise---with each element's DOFs
stored contiguously.  Because the array is a concatenation of
per-element DOF blocks, the following rules apply:

\begin{itemize}[leftmargin=2em]
\item \texttt{DofStorage\_t = Independent} is the layout's natural
  reading and requires no additional metadata.  It is the expected
  value for volume DG and spectral-element blocks.

\item \texttt{DofStorage\_t = Shared} is permitted \emph{only} when
  the block's element set consists of interface (face or edge)
  elements, listed explicitly by a \texttt{PointList} or
  \texttt{PointRange} over the element indices of the corresponding
  face or edge \texttt{Elements\_t} section(s).  The shared reading is
  then: each listed interface element's DOF block is shared between the
  volume elements adjacent to it.  This is the HDG trace case
  the trace case.

\item \texttt{DofStorage\_t = Shared} on a block whose element set is
  the zone's volume elements---in particular, any
  \texttt{InterpolationPoints} block with \emph{no} point set---is
  \textbf{invalid}.  Under that sizing each interface DOF would appear
  once per adjacent volume element, which contradicts the definition of
  \texttt{DofStorageShared}.  \texttt{cgnscheck} should report this as an error
  (Section~\ref{sec:cgnscheck}).
\end{itemize}

\section{Interaction with CPEX 0047 (Integration Points)}
%% ═════════════════════════════════════════════════════════════════════════

CPEX~0047~\cite{cpex0047} introduces
\texttt{GridLocation\_t = IntegrationPoint}, quadrature-rule
definitions, and an \texttt{ItgPointsStartOffset} array giving the
starting position of each element's integration-point data within the
solution array.  It permits that grid location under
\texttt{FlowSolution\_t}, \texttt{ZoneSubRegion\_t}, \texttt{BC\_t},
and \texttt{BCDataSet\_t}.

The two proposals are complementary.  \texttt{ItgPointsStartOffset} is
precisely the per-element offset array whose absence motivates
Section~\ref{sec:shared-vertex-layout}, and where it applies it is the
better mechanism---this CPEX recommends it over the redundant
\texttt{PointList} encoding.  Because integration points are interior to
elements and the offset array assigns each element a disjoint slice,
\texttt{DofStorageIndependent} is the only valid value under that grid location;
recording it aids uniform reader dispatch but adds nothing derivable,
and \texttt{DofStorageShared} there should be a \texttt{cgnscheck} error.  Neither
proposal subsumes the other: 0047 says nothing about vertex-, edge-, or
face-located DOFs, which is the only place a storage discriminator is
load-bearing, and does not cover \texttt{DiscreteData\_t}.  Conversely,
0047 extends \texttt{BC\_t} and \texttt{BCDataSet\_t} where this CPEX
deliberately does not (Design Decision~\ref{dd:bcdata}), and its
\texttt{IntegrationPoint} location already covers element-local boundary
data, including the weakly-imposed boundary conditions of continuous
methods.

One editorial concern spans the two proposals: CPEX~0045's
\texttt{InterpolationPoints} and CPEX~0047's \texttt{IntegrationPoint}
are similar names for different \texttt{GridLocation\_t} values.  That
is a matter for the editors of those proposals, but readers of this one
should note the distinction.

%% ═════════════════════════════════════════════════════════════════════════
\section{Backward Compatibility}
\label{sec:compat}
%% ═════════════════════════════════════════════════════════════════════════

\begin{itemize}[leftmargin=2em]
\item \textbf{Existing files:} Fully compatible.  The
  \texttt{DofStorage} node is optional; its absence is
  equivalent to \texttt{DofStorageNull}.  No existing file
  is invalidated.

\item \textbf{Existing readers:} Unaffected.  Per the CGNS convention,
  readers silently ignore unknown child nodes.  An older library
  reading a file with \texttt{DofStorage} nodes will
  simply skip them.  \texttt{cgnscheck} validates only the child
  labels it knows about and does not enumerate or warn on unrecognized
  ones, so existing validation runs are unaffected as well.

\item \textbf{Existing writers:} Unaffected.  Codes that do not call
  the new API functions produce files without
  \texttt{DofStorage} nodes, identical to the current
  behavior.

\item \textbf{Newer-to-older direction:} A file written by a future
  library with an additional \texttt{DofStorage\_t} value will be read
  by a CPEX-0050-era library as \texttt{DofStorageUserDefined} with a
  warning, not an error, because \texttt{cgi\_DofStorage} follows
  \texttt{cgi\_GridLocation}'s forward-compatibility rule.

\item \textbf{ABI:} The \texttt{cgns\_sol}, \texttt{cgns\_discrete},
  \texttt{cgns\_subreg}, and \texttt{cgns\_user\_data} structures each
  grow by one \texttt{int}-sized enum field.
  This is an ABI change requiring recompilation of code that directly
  accesses the internal structures.  The public API is purely additive
  (new functions, new enum), so no existing function signatures change.
\end{itemize}

\subsection{Parallel I/O}

No new \texttt{cgp\_*} functions are required, but the constraint under
which the serial functions may be used in a parallel program must be
stated explicitly.

The parallel MLL (\texttt{pcgnslib.c}) contains no handling of
\texttt{GridLocation}, \texttt{DataClass}, or any other scalar metadata
child; such nodes are written by the serial MLL even in parallel
programs.  \texttt{DofStorage} follows suit.  Because writing it
creates---and, on modify, deletes---an HDF5 group, and HDF5 structural
modification under MPI-IO is a collective operation:

\begin{itemize}[leftmargin=2em]
\item \texttt{cg\_dof\_storage\_write} \textbf{shall} be called by all
  ranks in the communicator, with identical arguments and from an
  identical current position.
\item The same applies to the \texttt{cg\_goto} call that establishes
  the position.
\item \texttt{cg\_dof\_storage\_read} may be called independently once
  the file is open, since it is served entirely from the in-memory
  structure populated at open time.
\end{itemize}

This is the same rule that already governs \texttt{cg\_sol\_write},
\texttt{cg\_gridlocation\_write}, and every other metadata-creating
serial call used alongside \texttt{cgp\_*} data transfers; it is stated
here because the proposal adds a new call subject to it.

\subsection{Interpreting Legacy Data (\texttt{DofStorageNull})}
\label{sec:legacy-inference}

\texttt{DofStorageNull} means \emph{unspecified}, not ``shared.''  A
reader must not silently substitute a default.  The following
inference rules are recommended---non-normatively---for readers that
must nevertheless act on files predating this CPEX:

\begin{description}[leftmargin=2em]
\item[\texttt{CellCenter}, \texttt{FaceCenter}, \texttt{EdgeCenter},
  \texttt{[IJK]FaceCenter}] Treat as
  \texttt{DofStorage\allowbreak Independent}.  There is
  exactly one value per entity and no shared-entity ambiguity.

\item[\texttt{Vertex} with $\texttt{DataSize} = \texttt{VertexSize}$]
  Treat as \texttt{DofStorageShared}.  Before this CPEX, the SIDS
  \texttt{DataSize} formula admitted no other layout at this size.

\item[\texttt{Vertex} with a \texttt{PointList}] Unspecified.  A
  legacy file gives no way to tell an independent-DOF layout from a
  genuine vertex subset.  Readers should surface the ambiguity rather
  than guess.

\item[\texttt{InterpolationPoints} (CPEX~0045)] Treat as
  \texttt{DofStorageIndependent}, per Section~\ref{sec:dofstorage-interp}.

\item[\texttt{IntegrationPoint} (CPEX~0047)] Treat as
  \texttt{DofStorageIndependent}.
\end{description}

Note that these rules make no ``assume shared for backward
compatibility'' blanket assumption: since most CFD files are
cell-centered finite volume, such an assumption would be wrong for the
majority of existing data.  Example~\ref{ex:dispatch} shows a reader
applying this dispatch.

%% ═════════════════════════════════════════════════════════════════════════
\section{Examples}
%% ═════════════════════════════════════════════════════════════════════════

All examples use the position-based API: \texttt{cg\_goto} to the
target node, then \texttt{cg\_dof\_storage\_write}.  Error checking is
omitted for brevity; production code must check every return value.

Example~\ref{ex:shared-vertex-dg} is the motivating case of
Section~\ref{sec:field-evidence}: the encoding it shows has no
alternative today, and it is the reason for this proposal.  The others
are shorter, and are included only to fix the calling conventions---the
shared/independent pair, the reader-side dispatch, the Fortran bindings,
and the remaining permitted parents.  Where they label a layout that the
grid location and sizing rules already determine, that is noted in place
rather than presented as a case requiring the node.

\subsection{Example 1: Writing a Shared-DOF (CG) Solution}
\label{ex:cg-write}

\begin{lstlisting}[language=C]
/* Create a vertex-located solution node */
int S, F;
cg_sol_write(fn, B, Z, "FlowSolution", CGNS_ENUMV(Vertex), &S);

/* Mark DOFs as shared (CG FEM) */
cg_goto(fn, B, "Zone_t", Z, "FlowSolution_t", S, "end");
cg_dof_storage_write(CGNS_ENUMV(DofStorageShared));

/* Write solution data (one value per mesh vertex, shared) */
cg_field_write(fn, B, Z, S, CGNS_ENUMV(RealDouble),
    "Pressure", pressure, &F);
\end{lstlisting}

\subsection{Example 2: Writing an Independent-DOF (DG) Solution}
\label{ex:dg-write}

\begin{lstlisting}[language=C]
/* Create an interpolation-point-located solution node.
 * Per CPEX 0045, a block covering the whole zone at uniform
 * order needs no point set; DataSize is the sum of the
 * per-element DOF counts over all zone elements. */
int S, F;
cg_sol_write(fn, B, Z, "FlowSolution_DG",
    CGNS_ENUMV(InterpolationPoints), &S);

/* Set polynomial order (CPEX 0045):
 * spatialOrder = 3, temporalOrder = 0 */
cg_sol_interpolation_order_write(fn, B, Z, S, 3, 0);

/* Mark DOFs as element-local */
cg_goto(fn, B, "Zone_t", Z, "FlowSolution_t", S, "end");
cg_dof_storage_write(CGNS_ENUMV(DofStorageIndependent));

/* Write element-local DOFs */
cg_field_write(fn, B, Z, S, CGNS_ENUMV(RealDouble),
    "Pressure", pressure_dg, &F);
\end{lstlisting}

\subsection{Example 3: Reading and Dispatching on DOF Storage Layout}
\label{ex:dispatch}

\begin{lstlisting}[language=C]
CGNS_ENUMT(DofStorage_t) layout;

cg_goto(fn, B, "Zone_t", Z, "FlowSolution_t", S, "end");
cg_dof_storage_read(&layout);

switch (layout) {
case CGNS_ENUMV(DofStorageShared):
    /* Shared DOFs: interpolate using global mesh connectivity */
    visualize_shared(fn, B, Z, S);
    break;

case CGNS_ENUMV(DofStorageIndependent):
    /* Element-local DOFs: render per-element, preserve jumps */
    visualize_independent(fn, B, Z, S);
    break;

case CGNS_ENUMV(DofStorageUserDefined): {
    /* Writer must have left a DofStorageDescription
     * descriptor identifying the convention. */
    char dname[CGIO_MAX_NAME_LENGTH+1];
    char *text = NULL;
    int nd, n;
    cg_ndescriptors(&nd);
    for (n = 1; n <= nd; n++) {
        cg_descriptor_read(n, dname, &text);
        if (text == NULL) continue;
        if (strcmp(dname, "DofStorageDescription") == 0)
            visualize_user_defined(fn, B, Z, S, text);
        cg_free(text);
        text = NULL;
    }
    break;
}

default:
    /* DofStorageNull: legacy file.  Apply the inference
     * rules of Section 6.2 -- do not assume DofStorageShared. */
    visualize_legacy(fn, B, Z, S);
    break;
}
\end{lstlisting}

\subsection{Example 4: Fortran Usage}
\label{ex:fortran}

\begin{lstlisting}[language=Fortran]
integer :: S, ier, layout

! Write a shared-DOF solution
call cg_sol_write_f(fn, B, Z, 'FlowSolution', Vertex, S, ier)
call cg_goto_f(fn, B, ier, 'Zone_t', Z, 'FlowSolution_t', S, 'end')
call cg_dof_storage_write_f(DofStorageShared, ier)

! Read the DOF storage layout back
call cg_goto_f(fn, B, ier, 'Zone_t', Z, 'FlowSolution_t', S, 'end')
call cg_dof_storage_read_f(layout, ier)
if (layout == DofStorageIndependent) then
    ! Element-local interpolation
end if
\end{lstlisting}

\subsection{Example 5: Independent DOFs on a Shared-Vertex Mesh}
\label{ex:shared-vertex-dg}

This example addresses the case where the mesh uses shared vertices
(enabling stream tracing and mesh walking via standard
\texttt{Elements\_t} connectivity), but each element stores its own
independent solution values at those vertices.  The
\texttt{DofStorage\_t} node is the flag that tells readers
the repeated vertex indices in the \texttt{PointList} are independent
DOFs, not duplicates.  The zone must be unstructured, the
\texttt{PointList} must cover every element, and the traversal order is
fixed by Section~\ref{sec:ordering-rule}.

\begin{lstlisting}[language=C]
/*
 * Given, for a single-section unstructured zone:
 *   cgsize_t nVerts;         shared vertices in the zone
 *   cgsize_t nElems;         elements in the zone
 *   int      nVertsPerElem;  vertices per element (fixed type)
 *   cgsize_t *elem_conn;     connectivity, nElems*nVertsPerElem,
 *                            1-based, ascending element index
 *   double   *pressure_dg;   nElems*nVertsPerElem values
 *
 * Total DOFs = nElems * nVertsPerElem  (not nVerts).
 */
cgsize_t nDofs = nElems * (cgsize_t)nVertsPerElem;
cgsize_t *point_list = (cgsize_t *)malloc(nDofs * sizeof(cgsize_t));
if (point_list == NULL) return 1;

/* The PointList is the connectivity traversed in ascending
 * element index order, each element's vertices in canonical
 * order.  For this single fixed-size section that is exactly
 * the connectivity array; a multi-section, MIXED, or NGON_n
 * zone requires the traversal of Section 3.8.3. */
{
    cgsize_t i;
    for (i = 0; i < nDofs; i++)
        point_list[i] = elem_conn[i];
}

/* Create the solution node with a PointList.  Vertex location
 * preserves shared-mesh connectivity for geometry operations,
 * while DataSize becomes nDofs rather than nVerts. */
int S, F;
cg_sol_ptset_write(fn, B, Z, "FlowSolution_DG",
    CGNS_ENUMV(Vertex), CGNS_ENUMV(PointList),
    nDofs, point_list, &S);

/* Mark as independent: values at repeated vertex indices are
 * independent across elements, ordered by ascending element
 * index then canonical vertex order. */
cg_goto(fn, B, "Zone_t", Z, "FlowSolution_t", S, "end");
cg_dof_storage_write(CGNS_ENUMV(DofStorageIndependent));

/* Write element-local solution data */
cg_field_write(fn, B, Z, S, CGNS_ENUMV(RealDouble),
    "Pressure", pressure_dg, &F);

free(point_list);
\end{lstlisting}

A reader distinguishes this from a shared-DOF solution as follows:

\begin{lstlisting}[language=C]
CGNS_ENUMT(DofStorage_t) layout;

cg_goto(fn, B, "Zone_t", Z, "FlowSolution_t", S, "end");
cg_dof_storage_read(&layout);

if (layout == CGNS_ENUMV(DofStorageIndependent)) {
    /* PointList entries are element-local DOF indices.
     * Values at the same vertex index from different elements
     * are independent -- do not average. */
}
\end{lstlisting}

\subsection{Example 6: Other Permitted Parent Nodes}
\label{ex:other-parents}

Usage on \texttt{DiscreteData\_t} and \texttt{ZoneSubRegion\_t} is
identical to \texttt{FlowSolution\_t}; only the \texttt{cg\_goto} path
differs.

\begin{lstlisting}[language=C]
/* DiscreteData_t: a cell-centered DG error indicator */
int D;
cg_discrete_write(fn, B, Z, "ErrorIndicator", &D);
cg_goto(fn, B, "Zone_t", Z, "DiscreteData_t", D, "end");
cg_gridlocation_write(CGNS_ENUMV(CellCenter));
cg_dof_storage_write(CGNS_ENUMV(DofStorageIndependent));
cg_array_write("ElementError", CGNS_ENUMV(RealDouble),
    1, &nElems, error_data);

/* ZoneSubRegion_t: per-face boundary fluxes.  The sub-region
 * dimension is one less than the zone's cell dimension, so query
 * the base rather than hard-coding it. */
char basename[CGIO_MAX_NAME_LENGTH+1];
int cellDim, physDim, SR;
cg_base_read(fn, B, basename, &cellDim, &physDim);
cg_subreg_bcname_write(fn, B, Z, "WallFluxes",
    cellDim - 1, "Wall_BC", &SR);
cg_goto(fn, B, "Zone_t", Z, "ZoneSubRegion_t", SR, "end");
cg_dof_storage_write(CGNS_ENUMV(DofStorageIndependent));
cg_array_write("HeatFlux", CGNS_ENUMV(RealDouble),
    1, &nBCFaces, heat_flux);
\end{lstlisting}

A single \texttt{cg\_goto} serves every subsequent call: neither
\texttt{cg\_gridlocation\_write}, \texttt{cg\_dof\_storage\_write}, nor
\texttt{cg\_array\_write} moves the current position.  Both layouts
above are already determined by the grid location and the sizing rules
(Section~\ref{sec:scope}); the node is written for uniformity, so that a
reader can dispatch on one query across every solution node in a file.
\subsection{Example 7: A Continuous Field Stored per Element}
\label{ex:continuous-independent}

A continuous spectral-element solver writing at
\texttt{InterpolationPoints} duplicates its interface DOFs, so the
storage is \texttt{DofStorageIndependent}; but the duplicated values agree, and a
post-processor may weld them.  Only the second node communicates that.

\begin{lstlisting}[language=C]
int S;
cg_sol_write(fn, B, Z, "FlowSolution",
    CGNS_ENUMV(InterpolationPoints), &S);

cg_goto(fn, B, "Zone_t", Z, "FlowSolution_t", S, "end");

/* Storage duplicates DOFs at element interfaces ... */
cg_dof_storage_write(CGNS_ENUMV(DofStorageIndependent));

/* ... but the duplicates agree: the field is C0 across interfaces. */
cg_interface_continuity_write(CGNS_ENUMV(InterfaceContinuous));
\end{lstlisting}

Replace the second call with \texttt{InterfaceDiscontinuous} and the
file describes a DG solution instead.  Every other item of metadata is
identical, which is precisely why the attribute is needed.  A reader
dispatches on the pair:

\begin{lstlisting}[language=C]
CGNS_ENUMT(DofStorage_t) storage;
CGNS_ENUMT(InterfaceContinuity_t) cont;
cg_dof_storage_read(&storage);
cg_interface_continuity_read(&cont);

if (storage == CGNS_ENUMV(DofStorageIndependent) &&
    cont    == CGNS_ENUMV(InterfaceContinuous)) {
    /* Safe to weld duplicated DOFs into a continuous field. */
} else {
    /* Preserve every value distinctly: either the jumps are
     * meaningful, or continuity was not asserted and must not
     * be assumed. */
}
\end{lstlisting}

\label{sec:sids-impact}

\begin{enumerate}[leftmargin=2em]
\item \textbf{New enumeration type:} \texttt{DofStorage\_t}
  is added to the SIDS Building-Block Structure Definitions

\item \textbf{\texttt{UserDefinedData\_t} amendment:} The

  similarly amended.

\item \textbf{\texttt{PointList} semantics amendment:} The description of
  \texttt{PointList} under \texttt{FlowSolution\_t} in SIDS~\S7.7 is

  \texttt{DofStorage\_t = Independent} and
  \texttt{GridLocation\_t = Vertex}, in unstructured zones only.
  Repeated indices in that context represent element-local DOFs and are
  not malformed duplicates.  The DOF-to-element mapping, the element
  traversal order, the treatment of \texttt{MIXED} type codes, the
  exclusion of \texttt{NFACE\_n}, the whole-zone coverage requirement,

\subsection{Writing Conventions}

The node is written only when the DOF storage layout is not
\texttt{DofStorageNull}; \texttt{DofStorageNull} is represented by the
absence of the node.  This mirrors \texttt{GridLocation}, which is
likewise omitted when it would carry its default.  The two differ in
what the absence \emph{means}: an absent \texttt{GridLocation} implies
the concrete value \texttt{Vertex}, whereas an absent
\texttt{DofStorage} implies only ``unspecified''
(Section~\ref{sec:legacy-inference}).

\texttt{InterfaceContinuity} follows the identical convention: written
only when not \texttt{InterfaceContinuityNull}, and absence meaning
``unspecified'' rather than any concrete value.  In particular, absence
must not be read as \texttt{InterfaceContinuous}.

When \texttt{DofStorageUserDefined} is written, the accompanying
description node is an ordinary \texttt{Descriptor\_t} and follows
the existing \texttt{Descriptor\_t} file mapping unchanged, with
name \texttt{DofStorageDescription}, label
\texttt{Descriptor\_t}, data type \texttt{C1}, dimension~1, and
cardinality 0,1 within the parent node.

\section{Design Decisions}
%% ═════════════════════════════════════════════════════════════════════════

Several design questions were evaluated during the development
of this proposal.  Each is addressed below with rationale grounded in
existing CGNS conventions and SIDS precedent.

\begin{enumerate}[leftmargin=2em]

\item \label{dd:bcdata} \textbf{Scope: \texttt{BCData\_t} is excluded.}
  \texttt{DofStorage\_t} is \emph{not} added to
  \texttt{BCData\_t}.  Boundary condition data arrays in
  \texttt{BCData\_t} are sized by the associated
  \texttt{PointList}/\texttt{PointRange} and \texttt{GridLocation\_t},
  which already determine the data layout unambiguously.  Adding
  \texttt{DofStorage\_t} to \texttt{BCData\_t} would therefore be
  redundant, and would introduce a potential inconsistency if the BC
  layout differed from the solution it constrains.

  No inference in the other direction is intended or valid: the layout
  of boundary data does \emph{not} follow from the DOF storage layout of
  the parent \texttt{FlowSolution\_t}, and weak imposition of boundary
  conditions is not a DG-specific technique.  Nitsche and penalty
  methods in continuous FEM and in isogeometric analysis routinely pair
  a \texttt{DofStorageShared} interior solution with element-local boundary data
  at face quadrature points.  Such data is already expressible:
  CPEX~0047 permits \texttt{GridLocation\_t = IntegrationPoint} under
  \texttt{BC\_t} and \texttt{BCDataSet\_t}, with
  \texttt{ItgPointsStartOffset} fixing the per-face layout, so no
  additional metadata is required for that case either.
  The \texttt{ZoneSubRegion\_t} extension introduced here
  partially addresses such cases: interface fluxes or
  surface-local fields that require a DOF storage label
  can be stored in a \texttt{ZoneSubRegion\_t} referencing the
  relevant boundary condition.

\item \textbf{Per-solution-node granularity (not per-field).}
  The DOF storage layout applies at the \texttt{FlowSolution\_t} level,
  meaning all \texttt{DataArray\_t} children share the same
  layout.  This follows the precedent set by
  \texttt{GridLocation\_t}, which is likewise a per-solution-node
  property: all fields within a \texttt{FlowSolution\_t} node share
  the same grid location.  Per-\texttt{DataArray\_t} granularity was
  rejected because it would add significant API and metadata
  complexity with no demonstrated need.  Solvers that genuinely mix
  layouts within a single zone (e.g., HDG methods with
  shared traces and independent volumes) should use separate
  \texttt{FlowSolution\_t} nodes, exactly as they would use separate
  nodes for fields at different \texttt{GridLocation\_t} values.

\item \label{dd:permissive} \textbf{Semantically inconsistent
  combinations are permitted but not enforced.}
  The MLL does \emph{not} enforce consistency between
  \texttt{DofStorage\_t} and \texttt{GridLocation\_t}.  Two
  combinations are defective, in different degrees:

  \begin{itemize}[leftmargin=1.5em]
  \item A \texttt{CellCenter} solution is inherently element-local, so
    \texttt{DofStorageShared} is \emph{meaningless} there---the single
    per-element DOF has no geometric support on the element boundary.
    \texttt{cgnscheck} should warn.
  \item \texttt{DofStorageShared} on an \texttt{InterpolationPoints} block whose
    element set is the zone's volume elements is \emph{invalid}, not
    merely odd: the sizing contradicts the definition of
    \texttt{DofStorageShared}, and, independently, CPEX~0045 supplies no
    DOF-to-sub-entity map with which sharing could be realized
    (Section~\ref{sec:dofstorage-interp}).  \texttt{cgnscheck} should
    report an error.
  \end{itemize}

  In neither case shall the library reject the combination on write.
  This follows the established
  CGNS convention of being permissive in what is accepted: the
  standard documents correct usage; validation is delegated to
  application-level tools such as \texttt{cgnscheck}
  (Section~\ref{sec:cgnscheck}).

\item \textbf{Position-based API rather than per-parent functions.}
  See Section~\ref{sec:mll} for the full rationale.  The decisive
  consideration is that the address-helper pattern used by every other
  optional scalar metadata child already solves parent dispatch,
  modify-mode overwrite, and absent-node reads, so reimplementing
  those three behaviors six times would add code without adding
  capability.

\item \textbf{A new node type rather than a new
  \texttt{GridLocation\_t} value.}  See
  Section~\ref{sec:why-new-node}.

\item \textbf{Two separate attributes rather than one combined
  enumeration.}  A single enumeration could in principle enumerate the
  meaningful pairs---\texttt{SharedContinuous},
  \texttt{IndependentContinuous}, \texttt{IndependentDiscontinuous}.
  Rejected for three reasons.  The two properties answer different
  questions, are supplied by different parts of a solver, and are known
  with different confidence: a writer almost always knows its storage
  layout, while continuity is an assertion about the discretization that
  it may not be in a position to make.  Combining them would force a
  writer that knows only the layout to either overstate its knowledge or
  say nothing at all.  A combined enumeration would also grow
  multiplicatively if either property later gains a value, and it would
  make the common case---recording storage alone, as every example
  before Example~\ref{ex:continuous-independent} does---depend on a
  decision about continuity that is irrelevant to it.  Orthogonal
  properties are recorded in orthogonal nodes, which is also how CGNS
  treats \texttt{GridLocation\_t} and \texttt{DataClass\_t}.

\end{enumerate}

\subsection{Rejected Alternatives}

\begin{description}[leftmargin=2em]
\item[A boolean \texttt{Discontinuous} flag.]  Rejected.  A boolean
  cannot express ``unspecified,'' which is exactly the state every
  pre-existing file is in, so a boolean would force writers to assert
  a layout they may not know.  It also leaves no room for a
  \texttt{UserDefined} escape hatch, and CGNS has no precedent for
  boolean-valued metadata nodes.

\item[A third \texttt{MixedStorage} value.]  Rejected; see the
  Rationale for Two-Value Classification.  Mixed-layout methods store
  distinguishable data and should store it in distinguishable nodes.

\item[Encoding the layout in \texttt{UserDefinedData\_t}.]  Rejected as
  the primary mechanism.  It requires every reader to agree on a name
  and string convention by side-channel, which is precisely the
  interoperability failure this CPEX exists to fix.  A standard
  enumeration with a standard label is machine-checkable;
  \texttt{UserDefinedData\_t} is not.  Note that this CPEX
  nevertheless \emph{permits} \texttt{DofStorage\_t} as a child of
  \texttt{UserDefinedData\_t}, so applications storing fields there
  can label them properly.

\item[Deriving the layout from array sizes.]  Not rejected, and worth
  stating accurately: for every encoding legal before this CPEX the
  layout \emph{is} determined by \texttt{GridLocation\_t} and the SIDS
  \texttt{DataSize} formula, irrespective of element mix
  (Section~\ref{sec:legacy-inference}).  A discriminator becomes
  necessary only once a second sizing is admitted at the same grid
  location, which is what the \texttt{Vertex} plus \texttt{PointList}
  encoding of Section~\ref{sec:shared-vertex-layout} does.  Outside
  that case the node is confirmatory, and is recommended for
  uniformity and self-description rather than required to resolve an
  ambiguity.

\item[Placing the node on \texttt{Zone\_t} or \texttt{Base\_t}.]
  Rejected.  A single zone routinely carries solutions with different
  layouts---an HDG solver's volume and trace blocks, for
  instance---so a zone-level
  setting could not express them.
\end{description}

\section{Recommended \texttt{cgnscheck} Validation Rules}
\label{sec:cgnscheck}
%% ═════════════════════════════════════════════════════════════════════════

Per Design Decision~\ref{dd:permissive}, the MLL is permissive and
validation belongs in \texttt{cgnscheck}.  The following rules are
recommended.  Note that the on-disk representation is a \texttt{C1}
string, so there is no such thing as an out-of-range integer value in
a file; the corresponding check is on the string.

\begin{description}[leftmargin=2em]

\item[Error:] \texttt{DofStorage} node data is not one of
  \texttt{"Null"}, \texttt{"UserDefined"}, \texttt{"DofStorageShared"},
  or \texttt{"DofStorageIndependent"}.  Note that the MLL itself reports this as an
  error via \texttt{cgi\_DofStorage} for files at or below the
  library's own version, and as a warning (degrading to
  \texttt{UserDefined}) for files written by a newer library.

\item[Error:] \texttt{InterfaceContinuity} node data is not one of
  \texttt{"Null"}, \texttt{"UserDefined"},
  \texttt{"InterfaceContinuous"}, or
  \texttt{"InterfaceDiscontinuous"}, with the same newer-library
  degradation as above.

\item[Error:] \texttt{DofStorage\_t = Shared} together with
  \texttt{InterfaceContinuity\_t = Discontinuous} --- contradictory,
  since a single shared storage slot cannot hold two differing values
  (Section~\ref{sec:continuity}).

\item[Warning:] \texttt{InterfaceContinuity} present on a node where no
  DOF duplication can occur---\texttt{GridLocation\_t = CellCenter}, or
  \texttt{Vertex} with no \texttt{PointList}---where the assertion is
  vacuous rather than wrong (Section~\ref{sec:continuity}).

\item[Warning, optional and off by default:] where the field arrays and
  the DOF correspondence are both available, \texttt{cgnscheck} may
  sample duplicated DOFs and warn when
  \texttt{InterfaceContinuity\_t = Continuous} but the sampled copies
  differ by more than a tolerance.  This check is necessarily partial:
  for arbitrary interpolation points the correspondence cannot be
  established at all (Section~\ref{sec:dofstorage-interp}), so a clean
  result is not a guarantee and a failure should be reported as a
  suspected inconsistency rather than a definite one.

\item[Error:] \texttt{DofStorage\_t = Independent} with
  \texttt{GridLocation\_t = Vertex} and \emph{no}
  \texttt{PointList} --- the SIDS \texttt{DataSize} formula yields
  \texttt{VertexSize} (the shared-vertex count), which cannot
  represent the larger element-local DOF count
  (Section~\ref{sec:shared-vertex-layout}).

\item[Error:] \texttt{DofStorage\_t = Independent} with
  \texttt{GridLocation\_t = Vertex} and a \texttt{PointList}, in a
  \emph{structured} zone --- the ordering rule is defined only for
  unstructured zones (Section~\ref{sec:ptlist-restrictions}).

\item[Error:] \texttt{DofStorage\_t = Independent} with
  \texttt{GridLocation\_t = Vertex} and a \texttt{PointList} whose
  contents do not equal the zone's element connectivity traversed per
  Section~\ref{sec:ordering-rule}.  Because the required contents are
  fully determined, this is an exact check, not a heuristic.  It
  subsumes checks for wrong length, wrong ordering, and incomplete
  element coverage.

\item[Error:] \texttt{DofStorage\_t = Independent} with
  \texttt{GridLocation\_t = Vertex} and a \texttt{PointList} in a zone
  containing an \texttt{NFACE\_n} section
  (Section~\ref{sec:ptlist-restrictions}).

\item[Error:] \texttt{Rind\_t} present alongside
  \texttt{DofStorage\_t = Independent},
  \texttt{GridLocation\_t = Vertex}, and a \texttt{PointList}
  (Section~\ref{sec:ptlist-restrictions}).

\item[Error:] \texttt{DofStorage\_t = Shared} with
  \texttt{GridLocation\_t = InterpolationPoints} and no point set, or
  with a point set that lists volume rather than interface element
  indices (Section~\ref{sec:dofstorage-interp}).

\item[Error:] \texttt{DofStorage\_t = Shared} with
  \texttt{GridLocation\_t = IntegrationPoint} --- integration-point
  data is necessarily element-local.

\item[Warning:] \texttt{DofStorage\_t = Shared} with
  \texttt{GridLocation\_t = CellCenter} (or \texttt{FaceCenter},
  \texttt{EdgeCenter}, \texttt{[IJK]FaceCenter}) --- semantically
  inconsistent, since such data is inherently one value per entity
  with no shared-entity ambiguity (Design
  Decision~\ref{dd:permissive}).  \textbf{Convention:} this
  combination should not be used.

\item[Warning:] \texttt{DofStorage\_t = Shared} on a
  \texttt{FlowSolution\_t} whose CPEX-0045 \texttt{InterpolationOrders}
  gives \texttt{spatialOrder = 0} --- a $p=0$ basis has no interface
  DOFs to share.

\item[Warning:] A value of \texttt{DofStorageUserDefined} without
  a sibling \texttt{Descriptor\_t} named
  \texttt{DofStorageDescription} --- the convention is then
  unrecoverable by any reader.

\item[Warning:] A \texttt{DofStorage} node whose data is
  \texttt{"Null"}.  This is legal but pointless: the absence of the
  node carries the same meaning, and writing \texttt{Null} through the
  MLL removes the node rather than creating one, so such a node
  indicates a file written outside the MLL.

\end{description}

\section{Reference Implementation, Versioning, and Test Plan}
\label{sec:refimpl}
%% ═════════════════════════════════════════════════════════════════════════

\subsection{Deliverables}

The reference implementation comprises:

\begin{enumerate}[leftmargin=2em]
\item \texttt{cgnslib.h}: the \texttt{DofStorage\_t} enumeration,
  \texttt{NofValidDofStorage}, the \texttt{DofStorageName} extern
  declaration, and prototypes for
  \texttt{cg\_dof\_storage\_read},
  \texttt{cg\_dof\_storage\_write}, and
  \texttt{cg\_DofStorageName}.
\item \texttt{cgnslib.c}: the \texttt{DofStorageName} table and the
  three public functions.
\item \texttt{cgns\_header.h}: the \texttt{dof\_storage} field in
  \texttt{cgns\_sol}, \texttt{cgns\_discrete}, \texttt{cgns\_subreg},
  and \texttt{cgns\_user\_data}; prototypes for
  \texttt{cgi\_dof\_storage\_address} and \texttt{cgi\_DofStorage}.
\item \texttt{cgns\_internals.c}: the address helper, the string
  mapper, and the four parser updates.
\item \texttt{cgns\_f.F90} / \texttt{cgns\_f.h}: the Fortran bindings
  and the \texttt{DofStorage\_t} parameter values.
\item \texttt{cgnscheck.c}: the validation rules of
  Section~\ref{sec:cgnscheck}.
\item \texttt{cgnsview}: display of the new node (no code change
  expected; the generic C1 node display suffices).
\item Documentation updates to the SIDS, File Mapping Manual, and MLL
  reference per Sections~8 and~9.
\end{enumerate}

\subsection{Versioning}

\textbf{Target release: CGNS 5.0, jointly with CPEX~0045.}  The two
proposals are being developed together for the same release.  This is a
deliberate choice rather than a scheduling coincidence: because the
\texttt{Vertex} encoding defined here and CPEX~0045's
\texttt{InterpolationPoints} can express overlapping cases
(Section~\ref{sec:scope}), implementing them in one pass is what
guarantees they use consistent vocabulary, that \texttt{cgnscheck}
validates both against the same model of DOF storage, and that the SIDS
text cannot describe the same data in contradictory terms.  Neither
proposal should be understood as the faster route to the capability.

The library version constant is incremented, and the value at which
\texttt{DofStorage\_t} and \texttt{InterfaceContinuity\_t} first appear
shall be recorded in the SIDS text
so that implementers can determine support from the file version
alone.  The forward-compatibility path described in
Section~\ref{sec:compat} depends on this: \texttt{cgi\_DofStorage} and
\texttt{cgi\_InterfaceContinuity} degrade unrecognized strings to
\texttt{UserDefined} only when \texttt{cg->version > CGNSLibVersion}.
Because both attributes are introduced in the same release, a single
version threshold serves both.

\subsection{Test Plan}

\begin{enumerate}[leftmargin=2em]
\item \textbf{Round trip, all parents, both attributes.}  For each of
  \texttt{FlowSolution\_t}, \texttt{DiscreteData\_t},
  \texttt{ZoneSubRegion\_t}, and \texttt{UserDefinedData\_t}: write
  each of \texttt{DofStorageShared}, \texttt{DofStorageIndependent}, and
  \texttt{DofStorageUserDefined}; close; reopen; read back and compare.
  Repeat for \texttt{InterfaceContinuous},
  \texttt{InterfaceDiscontinuous}, and
  \texttt{InterfaceContinuityUserDefined}.

\item \textbf{Independence of the two attributes.}  Write each of the
  nine combinations of the two enumerations (including
  \texttt{Null} for each) on one node; verify that reading either is
  unaffected by the other, that writing one does not create or remove
  the other, and that writing \texttt{Null} to one leaves the other
  intact.  This is the regression test for the shared address-helper
  mechanism.

\item \textbf{Absent node.}  Read from a node with no
  \texttt{DofStorage} child and assert \texttt{CG\_OK} with
  \texttt{DofStorageNull}.  Repeat against a file written by a
  pre-CPEX-0050 library.

\item \textbf{Overwrite in \texttt{CG\_MODE\_MODIFY}.}  Write
  \texttt{DofStorageShared}, close, reopen in modify mode, write
  \texttt{DofStorageIndependent}, close, reopen: assert the value is
  \texttt{DofStorageIndependent} \emph{and} that the parent has exactly one
  child with label \texttt{DofStorage\_t}.  This is the regression
  test for duplicate-child creation.

\item \textbf{Deletion.}  Write \texttt{DofStorageShared}, then write
  \texttt{DofStorageNull} in modify mode; assert the child node is
  gone and a subsequent read yields \texttt{DofStorageNull}.

\item \textbf{Invalid input.}  Assert \texttt{CG\_ERROR} from
  \texttt{cg\_dof\_storage\_write} for out-of-range enum values.

\item \textbf{Wrong parent.}  Assert \texttt{CG\_INCORRECT\_PATH} when
  the current position is, e.g., \texttt{GridCoordinates\_t}.

\item \textbf{No current position.}  Assert \texttt{CG\_ERROR} when
  called without a preceding \texttt{cg\_goto}.

\item \textbf{Forward compatibility.}  Hand-construct a file
  (via CGIO) with \texttt{DofStorage} data \texttt{"Trace"} and a
  version greater than the library's; assert the read yields
  \texttt{DofStorageUserDefined} with a warning, not an error.  With a
  version at or below the library's, assert \texttt{CG\_ERROR}.

\item \textbf{Shared-vertex independent layout.}  Build the
  Example~\ref{ex:shared-vertex-dg} file; assert
  \texttt{cg\_sol\_ptset\_info} reports
  $\texttt{npnts} = n_{\mathrm{elem}} \times n_{\mathrm{vpe}}$, that
  \texttt{cg\_field\_read} returns all values, and that
  \texttt{cgnscheck} passes.  Then perturb the \texttt{PointList}
  ordering and assert \texttt{cgnscheck} reports an error.

\item \textbf{\texttt{cgnscheck} rules.}  One file per rule in
  Section~\ref{sec:cgnscheck}, asserting the expected error or
  warning.

\item \textbf{Fortran.}  Mirror tests 1--4 through the Fortran
  bindings.

\item \textbf{Parallel.}  Under \texttt{cgp\_open}, call
  \texttt{cg\_dof\_storage\_write} collectively from all ranks and
  assert the file is valid and single-valued; confirm on 1, 2, and 4
  ranks.

\item \textbf{Backward compatibility of existing tests.}  The full
  existing CGNS test suite shall pass unchanged.
\end{enumerate}
